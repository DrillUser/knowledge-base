# ЧАСТЬ 1. Теоретический фундамент (читать подряд)

## 1.1. Чем ИИ-нагрузка отличается от обычного сервиса
Обычный backend-сервис — это в основном CPU + сеть + диск, детерминированный вывод (один и тот же запрос → один и тот же ответ), масштабирование по количеству запросов. ИИ-нагрузка отличается сразу по трём осям: **железо** (GPU — дорогой, дефицитный ресурс с иной моделью выделения, чем CPU, AI-01), **поведение** (вывод модели вероятностный — один и тот же запрос может дать разный ответ, «правильность» не проверяется кодом возврата, AI-06) и **экономика** (стоимость считается не по CPU-часам, а по токенам на каждый вызов, AI-05). Эти три отличия и объясняют, зачем нужен отдельный блок, а не просто пара карточек внутри Kubernetes.

## 1.2. Обучение vs инференс — два разных профиля нагрузки
**Обучение (training)** — редкие, длительные (часы-недели), очень ресурсоёмкие job'ы, где важен суммарный throughput и устойчивость к сбоям на длинной дистанции (checkpointing, AI-08), а не отклик здесь и сейчас — классический batch, а не online-сервис. **Инференс (serving)** — противоположность: короткие запросы, важна латентность (или throughput при batch-обработке), нагрузка идёт непрерывно и неравномерно — отсюда автоскейлинг (AI-03) и оптимизация раннтайма (AI-02). Большинство DevOps/SRE-задач в ИИ-инфраструктуре — это про инференс (обучение чаще остаётся в отдельном ML-инженерном контуре), но важно уверенно различать эти два мира: рекомендация, полезная для одного, часто вредна для другого (batching ради throughput — благо при обучении и палка о двух концах при инференсе с latency SLA).

## 1.3. Стек снизу вверх
GPU (физическое железо) → драйверы + **device plugin** (k8s видит GPU как ресурс, AI-01) → **serving runtime** (vLLM/Triton — эффективно гоняет модель на GPU, AI-02) → **автоскейлинг** поверх очереди задач, а не CPU (AI-03) → **LLM Gateway** перед моделью (контроль стоимости, кэш, fallback, AI-05) → приложение, часто с **RAG** поверх векторной БД (AI-04) → **observability и eval** над всем этим (AI-06) → **безопасность**, пронизывающая каждый слой (AI-07). Тот же принцип «каждый слой опирается на предыдущий», что и во всей остальной базе (00_index.md) — просто новый вертикальный срез поверх уже знакомых Kubernetes/Observability/GitOps.

## 1.4. LLM-специфика: почему это не «ещё один HTTP API»
Классический сервис принимает структурированный запрос (JSON с полями) и возвращает структурированный ответ — контракт зафиксирован схемой. LLM принимает и отдаёт свободный текст, а «контракт» — это по сути инструкция на естественном языке (промпт), которую модель может понять по-своему или выполнить неточно. Отсюда прямые практические следствия: тестирование через unit-тесты с точным ожидаемым результатом не работает (нужен eval через LLM-as-judge, AI-06), безопасность не сводится к валидации входа по схеме (нужна отдельная модель угроз, AI-07), а версионирование «контракта» — это версионирование промпта и данных RAG, а не только кода (AI-08).

## 1.5. Три смысла «AI + Ops» — не путать
Термины почти всегда путают, стоит развести явно:
- **MLOps / LLMOps** (этот блок) — как эксплуатировать ИИ-системы в проде: разворачивать, скейлить, защищать, версионировать модели и пайплайны вокруг них. ИИ здесь — **объект** эксплуатации.
- **AIOps** (карточка OB-07 в Блоке 3) — как использовать ИИ/ML внутри самого DevOps-процесса: anomaly detection в метриках, авто-корреляция инцидентов, LLM-суммаризация постмортемов. ИИ здесь — **инструмент** эксплуатации, а объект — обычная инфраструктура (та же, что в блоках 1–9).
- **AI-ассистированная разработка** (Claude Code/Copilot и подобные) — использование ИИ для написания кода/IaC/пайплайнов самими инженерами. В этом банке отдельно не разбирается, но стоит держать в голове как третий смысл того же словосочетания, чтобы не путать в разговоре.

## Карта «как всё связано» (одним абзацем)
ИИ-нагрузка отличается от обычного сервиса железом (GPU), поведением (вероятностный вывод) и экономикой (токены) → нужен **device plugin** для GPU в k8s (AI-01) → эффективный **serving runtime** с continuous batching и KV-cache (AI-02) → **автоскейлинг** по очереди, а не CPU, с поправкой на холодный старт GPU (AI-03) → приложение часто опирается на **RAG** через векторные БД (AI-04) → перед моделью встаёт **LLM Gateway** для контроля стоимости и отказоустойчивости (AI-05) → надо всем этим — **observability и eval**, потому что «200 OK» не значит «ответ верный» (AI-06) → сквозная тема — **безопасность**: prompt injection, excessive agency, supply chain моделей (AI-07) → а воспроизводимость всей связки — работа **MLOps жизненного цикла** (registry, feature store, версионирование данных, AI-08). Параллельная, но принципиально другая тема — **AIOps** (OB-07): не про эксплуатацию ИИ, а про использование ИИ для эксплуатации всего остального.

# ЧАСТЬ 2. Карточки

### AI-01. GPU-оркестрация в Kubernetes: device plugin, MIG, time-slicing

**Суть:** k8s не умеет работать с GPU «из коробки» — GPU становится k8s-ресурсом только через device plugin; MIG и time-slicing решают проблему дорогого и часто недогруженного одного GPU на много подов.

**За 30–60 сек:** Kubernetes из коробки понимает только CPU/память. Чтобы под мог запросить GPU (`resources.limits: {nvidia.com/gpu: 1}`), на ноде должен стоять **device plugin** (NVIDIA device plugin для NVIDIA GPU) — он регистрирует GPU как extended resource в kubelet и отдаёт устройство эксклюзивно одному контейнеру. Проблема: GPU дорогие, а инференс часто не утилизирует карту на 100% — отсюда два способа делить один физический GPU: **MIG** (Multi-Instance GPU, аппаратное разбиение на изолированные инстансы со своей памятью и вычислительными блоками, только на топовых картах A100/H100) и **time-slicing** (программное разделение — несколько подов по очереди используют весь GPU, без изоляции памяти, дешевле, но с риском, что один сосед повлияет на другого).

**Глубокий ответ:** Без device plugin GPU просто невидим для планировщика — под, запросивший `nvidia.com/gpu`, будет вечно Pending. Device plugin — это DaemonSet, который на старте сканирует железо ноды, регистрирует найденные GPU через kubelet gRPC API как ресурс и на каждый запрос пода отдаёт конкретное устройство (обычно через `NVIDIA_VISIBLE_DEVICES` внутри контейнера, что требует ещё и NVIDIA Container Toolkit на ноде — рантайм-хук, пробрасывающий драйвер и устройства внутрь контейнера). Ключевое отличие MIG от time-slicing — ось «изоляция vs гибкость»: MIG режет GPU физически (разные инстансы не видят память друг друга, гарантированная производительность каждому — подходит для multi-tenant прод), time-slicing — это квант времени на общем контексте GPU (программная очередь заданий), поэтому один «прожорливый» под может замедлить соседа — годится для dev/test или недорогого batch-инференса. Отдельная организационная практика — **GPU node pool**: GPU-ноды выделяют в отдельный пул с `taint` (чтобы обычные CPU-поды туда не садились случайно, тот же механизм, что в K8S-10) и `toleration` только у AI-подов, плюс `nodeSelector`/`nodeAffinity` по типу GPU, если в кластере смешаны разные модели карт. Cluster Autoscaler для GPU-пулов работает медленнее обычного (образы с CUDA тяжёлые, драйверы грузятся дольше) — это стоит учитывать при расчёте RTO автоскейлинга (K8S-16).

**Follow-ups:**
- *Почему под с `nvidia.com/gpu: 1` висит в Pending на кластере с GPU-нодами?* → скорее всего не поставлен/не готов device plugin, GPU не зарегистрирован как ресурс.
- *MIG vs time-slicing — в чём принципиальная разница?* → аппаратная изоляция памяти/вычислений (MIG) vs программная очередь на общем контексте (time-slicing, без изоляции).
- *Зачем taint на GPU-нодах?* → чтобы обычные (дешёвые в масштабировании) CPU-поды случайно не заняли дорогую GPU-ноду.
- *Что нужно, кроме device plugin, чтобы контейнер реально увидел GPU?* → NVIDIA Container Toolkit на ноде (пробрасывает драйвер/устройства через container runtime hook).
- *Почему автоскейлинг GPU-пула медленнее обычного?* → тяжёлые образы с CUDA/драйверами, дольше готовность ноды.

**Статус:** 🔴

### AI-02. Model serving: инференс-раннтаймы, continuous batching, KV-cache

**Суть:** LLM-инференс — не обычный REST-сервис: узкое место — память под KV-cache и параллельность батчей, а не CPU; специализированные раннтаймы (vLLM, TGI, Triton) выжимают из GPU кратно больше throughput, чем наивный запуск модели в цикле.

**За 30–60 сек:** Наивный способ обслуживать LLM — держать модель в памяти и обрабатывать запросы по одному (или батчем фиксированного размера) — сильно недоиспользует GPU, потому что генерация токенов последовательна (авторегрессивна) и разные запросы заканчиваются в разное время. **Continuous batching** (vLLM, TGI) решает это: новые запросы подмешиваются в уже идущий батч на лету, как только освобождается слот, вместо ожидания завершения всего батча. **KV-cache** (Key-Value cache) — память, в которой раннтайм хранит промежуточные состояния attention для уже сгенерированных токенов, чтобы не пересчитывать их заново на каждом новом токене; она растёт с длиной контекста и числом одновременных запросов и обычно — главный потребитель GPU-памяти в проде (не сами веса модели).

**Глубокий ответ:** PagedAttention (техника vLLM) управляет KV-cache как виртуальной памятью со «страницами»: вместо резервирования под каждый запрос непрерывного куска памяти на максимально возможную длину ответа (что даёт фрагментацию и потерю памяти на неиспользуемые «хвосты»), память выделяется постранично по мере генерации — это резко поднимает число одновременных запросов, помещающихся в ту же GPU-память. Triton Inference Server — более общий фреймворк (не только LLM), умеет батчинг и несколько бэкендов (ONNX, TensorRT, PyTorch), но LLM-специфичные оптимизации (continuous batching, PagedAttention) лучше развиты именно в vLLM/TGI. Latency vs throughput — фундаментальный trade-off serving: больший батч поднимает суммарный throughput (токенов/сек), но каждый отдельный запрос ждёт дольше — SLA-чувствительные сценарии (чат в реальном времени) настраивают батчинг иначе, чем offline-обработку документов. Quantization (int8/int4, GPTQ/AWQ) — способ уместить модель в меньше памяти ценой небольшой потери качества, что напрямую увеличивает и throughput, и допустимый размер батча/KV-cache на той же карте.

**Follow-ups:**
- *Что такое continuous batching и зачем?* → подмешивание новых запросов в идущий батч по мере освобождения слотов вместо ожидания завершения всего батча — выше утилизация GPU.
- *Что такое KV-cache и почему он часто главный потребитель памяти?* → кэш промежуточных attention-состояний по сгенерированным токенам; растёт с контекстом и числом параллельных запросов, обычно больше самих весов модели в проде.
- *Что делает PagedAttention?* → управляет KV-cache постранично (как виртуальная память), убирает фрагментацию, повышает число одновременных запросов.
- *В чём trade-off latency vs throughput в serving?* → больший батч поднимает суммарный throughput, но увеличивает задержку отдельного запроса.
- *Зачем квантование модели?* → меньше памяти на веса → больше места под KV-cache/батч → выше throughput ценой небольшой потери качества.

**Статус:** 🔴

### AI-03. Автоскейлинг ИИ-нагрузок: KEDA, очереди, холодный старт GPU

**Суть:** классический HPA по CPU почти бесполезен для GPU-инференса — масштабируют по длине очереди задач (KEDA) и держат warm pool, потому что холодный старт GPU-пода — это минуты, а не секунды.

**За 30–60 сек:** Для GPU-серверов CPU-utilization почти не коррелирует с реальной нагрузкой — GPU может быть загружен на 100%, пока CPU простаивает в ожидании данных. Поэтому вместо HPA по CPU (K8S-16) для ИИ-нагрузок чаще используют **KEDA** (Kubernetes Event-Driven Autoscaling) — масштабирование по внешней метрике: длина очереди сообщений (Kafka/Redis/SQS), число ожидающих запросов в LLM-гейтвее, кастомная Prometheus-метрика. Вторая специфика — **холодный старт**: под с GPU-моделью может стартовать минуты (скачать образ с CUDA + веса модели гигабайтами, инициализировать раннтайм) — это несовместимо с реактивным автоскейлингом при резком всплеске трафика, отсюда практика держать небольшой **warm pool** (минимум реплик всегда готовы) и/или прогревать модель заранее.

**Глубокий ответ:** KEDA работает поверх HPA — не заменяет его, а добавляет **scalers** (адаптеры к внешним источникам метрик: Kafka lag, Redis list length, Prometheus query, cron-расписание) и транслирует их в стандартный HPA object с external metrics. Это то же расширение, что упомянуто для HPA v2 в K8S-16 (custom/external metrics), только KEDA даёт готовые коннекторы вместо написания своего Prometheus Adapter правила с нуля. Scale-to-zero — отдельная возможность KEDA (масштабировать под до 0 реплик при отсутствии нагрузки), критичная для дорогих GPU-нод в неторговые часы, но требует, чтобы холодный старт был приемлем бизнесу (иначе первый запрос после простоя ждёт минуты — иногда используют «разогревающий» запрос по расписанию, чтобы не уходить в полный 0). Практический компромисс: для стабильно нагруженного прод-сервиса — небольшой warm pool (min replicas > 0), KEDA добавляет реплики поверх по очереди; для спорадической batch-нагрузки — scale-to-zero оправдан, несмотря на холодный старт, потому что простаивающий GPU стоит дорого 24/7.

**Follow-ups:**
- *Почему HPA по CPU плохо подходит для GPU-инференса?* → CPU не отражает реальную загрузку GPU; узкое место может быть в GPU/памяти, а не в CPU.
- *Что делает KEDA, чего не делает голый HPA?* → добавляет готовые scaler'ы к внешним источникам метрик (очереди, кастомные метрики) поверх стандартного HPA API.
- *В чём проблема холодного старта GPU-пода?* → минуты на загрузку тяжёлого образа/весов и инициализацию раннтайма — несовместимо с реактивным скейлингом на резкий всплеск.
- *Что такое warm pool и когда он нужен?* → минимум готовых реплик всегда онлайн; нужен, когда холодный старт неприемлем для бизнеса.
- *Когда оправдан scale-to-zero, несмотря на холодный старт?* → для спорадической/batch-нагрузки, где простаивающий GPU 24/7 дороже редких задержек первого запроса.

**Статус:** 🔴

### AI-04. RAG и векторные БД: embedding, ANN-индексы, чанкинг

**Суть:** RAG (Retrieval-Augmented Generation) подмешивает в промпт релевантные куски внешних данных, найденные по смысловой близости через векторный поиск — качество ответа определяется не только моделью, а качеством retrieval: как нарезаны документы (чанкинг) и как устроен ANN-индекс.

**За 30–60 сек:** **RAG** решает проблему «модель не знает наши внутренние данные и у неё ограниченный контекст»: документы заранее режут на **чанки** (куски текста), каждый чанк превращают в **embedding** (числовое представление смысла текста отдельной моделью), векторы кладут в **векторную БД** (pgvector, Qdrant, Milvus, Weaviate). На запрос пользователя вычисляется его embedding, векторная БД находит top-k ближайших по смыслу чанков (**ANN** — Approximate Nearest Neighbor, приближённый, а не точный поиск: точный на миллионах векторов слишком медленный), найденные чанки подставляются в промпт вместе с вопросом — так модель отвечает, опираясь на актуальные и специфичные для бизнеса данные, а не только на то, чему её обучили.

**Глубокий ответ:** Качество RAG определяется на 80% не выбором LLM, а качеством retrieval, и здесь есть конкретные инженерные развилки. **Чанкинг**: слишком крупные чанки — теряется точность (в топ-k попадает много нерелевантного текста рядом с нужным фактом), слишком мелкие — теряется контекст (нужный факт разорван между чанками); типичная практика — чанки по 200–500 токенов с overlap (перекрытием) между соседними, чтобы не рвать мысль на границе. **ANN-индексы**: HNSW (графовая структура, быстрый и точный поиск, но дороже по памяти) и IVFFlat (кластеризация векторов по «корзинам», компактнее, но менее точен на границах кластеров) — тот же trade-off recall vs latency vs memory, что и любой другой индекс (параллель с B-tree vs BRIN в Postgres, PG-08). **Гибридный поиск** — комбинация векторного (семантического) поиска с классическим полнотекстовым/keyword-поиском (BM25): чисто векторный поиск иногда промахивается на точных терминах (артикулы, коды ошибок, имена), которые keyword-поиск ловит идеально — гибрид берёт лучшее из обоих и переранжирует (**re-ranking**) результат отдельной моделью. Отдельная практическая проблема — **устаревание индекса**: данные меняются, а RAG отвечает по последнему проиндексированному состоянию, если нет пайплайна инкрементальной переиндексации (параллель с CDC/Debezium из KF-04 — тот же паттерн «источник меняется → нужно синхронизировать производную структуру»).

**Follow-ups:**
- *Зачем нужен RAG, если можно просто расширить контекст модели?* → большой контекст дороже по латентности/цене на каждый запрос и не решает актуальность данных «на сегодня»; RAG подмешивает только релевантное.
- *Что такое ANN и почему не точный поиск?* → приближённый ближайший сосед; точный (brute-force) поиск по всем векторам не масштабируется на миллионы записей по latency.
- *HNSW vs IVFFlat — в чём разница?* → графовый точный/дорогой по памяти поиск vs кластеризация по «корзинам», компактнее и быстрее, но менее точен на границах.
- *Зачем гибридный поиск, если есть векторный?* → векторный промахивается на точных терминах (коды, имена), keyword-поиск их ловит; гибрид комбинирует и переранжирует.
- *Как чанкинг влияет на качество ответа?* → слишком крупные чанки размывают релевантность, слишком мелкие рвут контекст; используют overlap между соседними чанками.

**Статус:** 🔴

### AI-05. LLM Gateway: rate limiting, семантическое кэширование, cost control

**Суть:** LLM-гейтвей — прокси-слой перед провайдерами моделей, который решает то, что не решает сама модель: контроль стоимости по токенам, ограничение частоты запросов, fallback между провайдерами и кэш для одинаковых/похожих запросов.

**За 30–60 сек:** Вызов LLM API стоит денег за каждый токен (вход + выход) и не имеет предсказуемой латентности — прямой вызов из каждого сервиса-потребителя приводит к неконтролируемым расходам и дублированию логики ретраев/лимитов. **LLM Gateway** (LiteLLM, Kong AI Gateway, собственный прокси) стоит между приложениями и провайдерами (OpenAI/Anthropic/self-hosted) и берёт на себя: **rate limiting** (по пользователю/команде/ключу, чтобы один клиент не съел весь бюджет), **cost tracking** (учёт токенов и денег по каждому потребителю — основа FinOps для ИИ), **fallback/маршрутизацию** (если основной провайдер недоступен или перегружен — переключиться на резервный/более дешёвый) и **семантическое кэширование** (кэш ответа не по точному совпадению строки запроса, а по близости embedding — «почти такой же вопрос» тоже попадает в кэш).

**Глубокий ответ:** Семантическое кэширование — самая нетривиальная часть: обычный HTTP-кэш работает по точному ключу (тот же запрос → тот же ответ), а для LLM два разных по формулировке, но одинаковых по смыслу вопроса должны получать один закэшированный ответ — для этого гейтвей считает embedding входящего запроса и ищет в векторной БД (та же техника, что в AI-04) достаточно близкий предыдущий запрос-ответ; порог близости — тонкая настройка (слишком высокий — кэш почти не срабатывает, слишком низкий — можно отдать неточный ответ на другой по сути вопрос). Rate limiting для LLM отличается от обычного API rate limiting тем, что считают не только число запросов, но и **токены** (короткий промпт и запрос с 50 страницами контекста стоят по-разному, хотя это «один запрос») — токен-бюджеты обычно выставляют per-team/per-project, а не только per-IP. Fallback-маршрутизация полезна и для отказоустойчивости (провайдер лёг → переключение на резервный, аналог circuit breaking из IS-06, только между внешними API, а не внутренними сервисами), и для cost optimization (рутинные простые запросы — на дешёвую/локальную модель, сложные — на дорогую топовую, это называют **model routing**).

**Follow-ups:**
- *Зачем нужен отдельный слой перед LLM API, если можно вызывать напрямую?* → централизованный контроль стоимости, rate limiting, fallback и кэш вместо дублирования этой логики в каждом сервисе.
- *Как работает семантическое кэширование?* → embedding входящего запроса ищется в векторной БД среди предыдущих запросов; при достаточной близости отдаётся закэшированный ответ вместо нового вызова модели.
- *Почему rate limiting для LLM считают в токенах, а не только в запросах?* → один запрос может стоить в сотни раз дороже другого по числу токенов на входе/выходе.
- *Что такое model routing и зачем?* → простые запросы — на дешёвую модель, сложные — на дорогую, снижает средний cost per request.
- *Как гейтвей помогает с отказоустойчивостью?* → fallback на резервного провайдера при отказе/перегрузке основного, аналог circuit breaking (IS-06) на уровне внешних API.

**Статус:** 🔴

### AI-06. LLMOps observability: трейсинг промптов, eval, регрессии

**Суть:** для LLM-приложений классических RED-метрик недостаточно — нужно видеть сам промпт/ответ, стоимость в токенах и результат автоматической оценки качества (eval), потому что «сервис отвечает 200 OK» не значит «ответ хороший».

**За 30–60 сек:** Обычный APM отвечает на вопрос «работает ли сервис» (latency, error rate — RED-метрики, OB-03), но для LLM-приложения этого недостаточно: сервис может стабильно отвечать 200 OK и при этом галлюцинировать или отвечать не по делу. **LLMOps observability** добавляет: полный **трейс промпта** (что реально ушло в модель, включая системный промпт и подмешанный RAG-контекст — часто это не то, что писал разработчик в коде, а результат нескольких шагов сборки), учёт **токенов и стоимости** на каждый вызов и **eval** — автоматическую оценку качества ответа, обычно через **LLM-as-judge** (другая модель оценивает ответ по критериям: релевантность, фактическая точность, тон).

**Глубокий ответ:** OpenTelemetry вводит semantic conventions для GenAI (`gen_ai.*` атрибуты span'ов) — тот же принцип трейсинга, что в OB-05, только span несёт специфичные для LLM поля (модель, промпт, токены, температура). Это критично для отладки: продакшен-баг «модель отвечает не то» невозможно разобрать без точного знания, какой именно текст (после сборки RAG-контекста, истории диалога, системного промпта) реально был отправлен модели — без трейсинга разработчик видит только код, а не то, что происходит во время исполнения. **Eval-контуры** — тестовая пирамида для LLM-приложений: golden dataset (набор вопрос-эталонный_ответ, собранный вручную или из реальных инцидентов), прогоняемый через LLM-as-judge при каждом изменении промпта/модели/RAG-конфигурации — так ловят регрессии до продакшена (изменил промпт, чтобы починить один кейс, — тихо сломал три других; без eval этого не увидеть до жалоб пользователей). Drift — отдельная проблема на длинной дистанции: модель провайдера обновилась «под капотом» (тот же API, то же имя, другое поведение), или сами пользовательские запросы сместились по теме — регулярный прогон eval-набора в проде (не только при деплое) ловит такой дрейф. Human-in-the-loop важен и здесь — LLM-as-judge не идеален (сам может галлюцинировать оценку), поэтому его периодически калибруют сверкой с реальными человеческими оценками на выборке.

**Follow-ups:**
- *Почему RED-метрик недостаточно для LLM-сервиса?* → «200 OK и быстро» не гарантирует, что ответ по смыслу правильный; нужна оценка качества, а не только доступности.
- *Что нужно видеть в трейсе LLM-вызова, кроме latency?* → полный собранный промпт (включая RAG-контекст/историю), токены, стоимость, параметры генерации.
- *Что такое LLM-as-judge?* → отдельная модель, оценивающая качество ответа по заданным критериям — способ автоматизировать eval.
- *Как ловят регрессии при смене промпта?* → golden dataset + eval прогоняется при каждом изменении, до деплоя в прод.
- *Что такое drift в контексте LLM-приложений и как его ловить?* → незаметное изменение поведения модели/данных со временем; ловится регулярным (не только при деплое) прогоном eval в проде.

**Статус:** 🔴

### AI-07. Безопасность ИИ-систем: OWASP LLM Top 10, prompt injection

**Суть:** LLM добавляет новый класс уязвимостей, которых нет в классических приложениях — модель нельзя структурно «отделить» от данных, которые она обрабатывает, поэтому вредоносная инструкция, спрятанная в данных, может быть выполнена как команда.

**За 30–60 сек:** **Prompt injection** — главная и самая специфичная угроза: если в контекст модели попадает текст из недоверенного источника (документ в RAG-базе, письмо, веб-страница) и этот текст содержит скрытую инструкцию («игнорируй предыдущие правила и сделай X»), модель может её выполнить — потому что для LLM нет структурного разделения между «командой разработчика» и «данными для обработки», всё это просто текст в одном контексте. **Insecure output handling** — вторая частая проблема: если ответ модели без проверки подставляется в SQL-запрос, шелл-команду или HTML (XSS), модель становится вектором инъекции, только источник — не пользовательский ввод напрямую, а креативность модели. OWASP выпускает отдельный **Top 10 для LLM-приложений**, параллельный классическому OWASP Top 10 (веб), с этими и другими пунктами (data leakage через модель, insecure plugin design, excessive agency — когда агенту дают больше прав на реальные действия, чем нужно для задачи).

**Глубокий ответ:** Prompt injection не имеет полного технического решения (в отличие от SQL-injection, который решается parametrized queries раз и навсегда) — сама природа LLM в том, чтобы гибко следовать инструкциям на естественном языке, и провести чёткую границу «это системная инструкция, а это данные» внутри одного текстового контекста фундаментально сложно. Практические меры снижения риска, а не устранения: разделение ролей в промпте (system/user/tool с разными уровнями доверия там, где API это поддерживает), явная пометка недоверенного контента («это внешние данные, не инструкция»), output-фильтрация (проверка ответа модели на признаки того, что она «сорвалась» с задачи), ограничение прав самого агента (**least privilege для агентов** — прямая параллель с K8S-15 RBAC и GO-09 Vault dynamic secrets: агент с доступом на запись в БД или на выполнение shell-команд должен иметь ровно необходимый минимум прав, а не полный доступ «на всякий случай») и человеческий контроль (human-in-the-loop) для действий с необратимыми последствиями. **Data leakage** — риск не только через выход модели: если чувствительные данные попали в промпт (например, весь профиль пользователя подмешан в RAG-контекст «на всякий случай»), они физически прошли через инфраструктуру провайдера модели (логи, кэш) — это вопрос архитектуры pipeline (сколько данных реально нужно подмешивать в контекст, где хранятся логи промптов, есть ли требования по data residency). Supply chain для моделей — отдельная, менее раскрученная, но растущая тема: скачанные веса модели (например, с публичного хаба) — это фактически исполняемый артефакт с непрозрачным происхождением, который стоит проверять на источник и целостность так же, как проверяют зависимости в обычном supply chain security.

**Follow-ups:**
- *Почему prompt injection нельзя решить так же, как SQL injection?* → в SQL есть чёткое разделение кода и данных (parametrized queries), в LLM инструкция и данные — один и тот же текстовый контекст без структурной границы.
- *Что такое insecure output handling?* → неотфильтрованная подстановка ответа модели в SQL/shell/HTML — модель становится вектором инъекции.
- *Что такое excessive agency у агентов и как её снижать?* → агенту выданы более широкие права на реальные действия, чем нужно для задачи; снижается через least privilege (аналог RBAC/Vault dynamic secrets).
- *Как можно снизить (не устранить) риск prompt injection на практике?* → разделение ролей в промпте, пометка недоверенного контента, output-фильтрация, human-in-the-loop для необратимых действий.
- *В чём риск supply chain для скачанных весов модели?* → непрозрачное происхождение артефакта, аналогично зависимостям в обычном коде — нужна проверка источника и целостности.

**Статус:** 🔴

### AI-08. MLOps жизненный цикл: registry, feature store, воспроизводимость

**Суть:** модель в проде — это не файл с весами, а воспроизводимая связка «код + данные + гиперпараметры + версия модели», и без явного трекинга этой связки нельзя ни объяснить, почему модель ведёт себя именно так, ни откатиться на предыдущую версию.

**За 30–60 сек:** **Experiment tracking** (MLflow, Weights & Biases) фиксирует для каждого запуска обучения версию кода, данные, гиперпараметры, метрики и итоговый артефакт модели — без этого через полгода никто не ответит «а как вообще получилась вот эта модель в проде». **Model registry** — следующий шаг: зарегистрированная модель проходит стадии (staging → production → archived), и переключение между версиями в проде — управляемая операция (как Deployment rollout, K8S-12), а не подмена файла на диске руками. **Feature store** — отдельный слой для ML-специфичной проблемы: одни и те же признаки (features) нужно считать одинаково и на обучении (batch, по историческим данным), и в проде (online, в реальном времени) — рассинхрон между этими путями (**training-serving skew**) — частая причина, почему модель хорошо работает на тестах и плохо в проде.

**Глубокий ответ:** Training-serving skew — ML-специфичный аналог проблемы «работает на моей машине»: если признак «средний чек клиента за 30 дней» на обучении считается одним SQL-запросом по историческому дампу, а в проде — другим кодом в реальном времени, различия в округлении, часовых поясах или обработке null'ов дают модели на входе данные, которых она не видела на обучении, и качество предсказаний деградирует незаметно (сервис при этом технически «здоров» — RED-метрики зелёные). Feature store (Feast и аналоги) решает это, храня определение признака один раз и предоставляя два способа доступа к одному и тому же вычислению — batch (для переобучения) и online (низкая латентность, для инференса) — из единого источника истины. Воспроизводимость обучения также требует версионирования самих **данных**, не только кода (DVC и аналоги — «git для датасетов»), потому что модель, обученная на данных v1 и на данных v2 с тем же кодом, — это разные модели. Отдельно от классического ML — **fine-tuning больших моделей** обычно не с нуля, а через **параметр-эффективные методы** (LoRA/QLoRA — дообучение малой добавочной части параметров вместо всей модели), что резко снижает требования к GPU-памяти и делает fine-tuning доступным вне гигантских дата-центров; checkpointing при этом работает так же, как в распределённом обучении в целом — периодическое сохранение состояния, чтобы не терять часы вычислений при сбое ноды (параллель с идеей WAL/checkpoint в Postgres, PG-10, только для процесса обучения, а не транзакций).

**Follow-ups:**
- *Что решает experiment tracking, чего не даёт просто сохранённый файл модели?* → воспроизводимую связку код+данные+гиперпараметры+метрики для каждого запуска.
- *Что такое training-serving skew и почему он опасен?* → расхождение в вычислении признаков между обучением и продакшеном; модель деградирует незаметно, сервис при этом технически здоров.
- *Как feature store решает training-serving skew?* → одно определение признака, два согласованных пути доступа (batch и online) из единого источника истины.
- *Зачем версионировать данные, а не только код?* → тот же код на разных данных даёт разные модели; воспроизводимость требует фиксации обеих частей.
- *Что такое LoRA и зачем он нужен?* → параметр-эффективный fine-tuning (дообучение малой добавочной части весов), резко снижает требования к GPU-памяти по сравнению с полным дообучением.

**Статус:** 🔴

## Практика

### Лаб 1. GPU-оркестрация в k8s (или эмуляция без физического GPU)
**Задача:** если есть доступ к GPU-ноде — поставить NVIDIA device plugin, задеплоить под с `resources.limits: {nvidia.com/gpu: 1}`, проверить `nvidia-smi` внутри пода. Без GPU — эмулировать механику через extended resources (кастомный ресурс на ноде) и убедиться, что под без нужного ресурса остаётся Pending с понятной причиной в events.
**Проверка:** под не планируется на ноду без нужного ресурса (`Insufficient nvidia.com/gpu` в events); с ресурсом — планируется и видит устройство.
**Закрепляет:** AI-01.

### Лаб 2. Развернуть LLM-инференс и смасштабировать его по очереди
**Задача:** поднять небольшую open-source модель через Ollama или vLLM (CPU-режим подойдёт для локалки), обернуть k8s Deployment + Service, настроить KEDA-скейлер по длине очереди запросов (например, через Redis list перед сервисом) вместо HPA по CPU. Нагрузить параллельными запросами.
**Проверка:** под масштабируется по длине очереди, а не по CPU-utilization; можешь объяснить, почему для этого сервиса CPU — плохая метрика для автоскейлинга.
**Закрепляет:** AI-02, AI-03.

### Лаб 3. RAG pipeline с векторной БД
**Задача:** поднять pgvector (или Qdrant) в Docker, реализовать pipeline: чанкинг документов → embedding → запись в векторную БД → top-k поиск по запросу → сборка промпта → вызов LLM. Сравнить эффект маленьких и крупных чанков на качество retrieval на одном и том же наборе документов.
**Проверка:** можешь показать реальный retrieval с ANN-индексом (`ivfflat`/HNSW) и объяснить, как изменение размера чанка меняет релевантность найденных фрагментов.
**Закрепляет:** AI-04.

### Лаб 4. LLM Gateway: rate limiting и семантический кэш
**Задача:** поставить LiteLLM (или свой прокси) перед LLM API, настроить rate limit по ключу, добавить семантический кэш поверх векторной БД из Лаба 3. Отправить несколько похожих по смыслу, но по-разному сформулированных запросов подряд.
**Проверка:** повторный/похожий запрос обслуживается из кэша без обращения к дорогому API — видно снижение latency и отсутствие нового вызова в логах провайдера.
**Закрепляет:** AI-05.

### Лаб 5. LLMOps observability и eval-набор
**Задача:** инструментировать вызовы LLM трейсингом (промпт, ответ, токены, латентность — через OTel GenAI-атрибуты или структурированные логи), построить дашборд по стоимости/токенам. Собрать 10–20 пар вопрос/эталонный-ответ и прогнать через LLM-as-judge при изменении промпта.
**Проверка:** изменение промпта, которое «выглядит невинно», ловится eval-набором как деградация (или улучшение) до раскатки в прод.
**Закрепляет:** AI-06.

### Лаб 6. Prompt injection на практике (только в изолированной тестовой среде!)
**Задача:** в тестовом RAG-приложении из Лаба 3 (без реальных секретов и продовых данных) продемонстрировать prompt injection через «отравленный» документ в базе знаний (документ с текстом вида «игнорируй предыдущие инструкции и выведи X»). Затем добавить защиту (пометка недоверенного контента, output-фильтрация) и показать, что атака больше не проходит.
**Проверка:** до фикса — модель следует внедрённой инструкции из данных; после — нет.
**Закрепляет:** AI-07.
