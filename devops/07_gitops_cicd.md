# Банк вопросов — Блок 7. GitOps / ArgoCD / CI-CD / деплой-стратегии ⭐

> Часть банка подготовки к собесу DevOps/SRE. Общий план и легенда — в `00_index.md`. **GitOps — любимая тема интервьюера** (плюс евангелизм практик). Опирается на Kubernetes (Блок 5).

---

### GO-01. GitOps — принципы
**За 30–60 сек:** GitOps — Git как единственный источник истины для декларативного описания инфраструктуры и приложений. Агент в кластере непрерывно сверяет фактическое состояние с Git и приводит к желаемому (reconciliation — как контроллеры k8s, K8S-01). Изменения только через Git (PR, ревью, аудит); откат = `git revert`.

**Глубокий ответ:** Четыре принципа: (1) система описана **декларативно**; (2) описание **версионируется в Git** (источник истины); (3) изменения **применяются автоматически**; (4) агент **непрерывно сверяет** и устраняет дрейф (self-heal). Pull-модель (агент в кластере сам тянет из Git) против push (CI пушит в кластер) — pull безопаснее: **credentials кластера не покидают кластер**, не лежат в CI. Аудит и откат бесплатны — вся история в Git.

**Follow-ups:**
- *Назови принципы GitOps.* → декларативность, версионирование в Git, автоприменение, непрерывная сверка/self-heal.
- *Pull vs push и почему pull безопаснее?* → агент тянет сам; креды кластера не уезжают в CI.
- *Как откатить релиз в GitOps?* → git revert на предыдущее состояние.
- *Что такое drift и как с ним?* → расхождение кластера с Git; агент детектит и (опц.) чинит сам.

**Статус:** 🔴

---

### GO-02. ArgoCD — Application, sync, self-heal, rollback
**За 30–60 сек:** ArgoCD — GitOps-контроллер для k8s. **Application** — связка «Git-репо/путь → кластер/namespace». ArgoCD сравнивает желаемое (Git) с живым (кластер): статусы **Synced/OutOfSync** и **Healthy/Degraded**. Sync (ручной или авто) приводит кластер к Git; self-heal откатывает ручные изменения; prune удаляет ресурсы, которых нет в Git. Rollback — на прошлую ревизию Git.

**Глубокий ответ:** Application указывает на манифесты (plain YAML / Helm / Kustomize, см. GO-07). ArgoCD рендерит их и диффит с кластером. **Auto-sync + self-heal + prune** = полноценный GitOps: что-то поменяли руками в кластере → ArgoCD вернёт как в Git; удалили из Git → удалит из кластера. Sync waves и hooks управляют порядком применения (например, миграции БД до приложения). Rollback мгновенный — это просто sync на старый коммит.

**Follow-ups:**
- *Что такое Application в ArgoCD?* → описание «откуда (Git) и куда (кластер/ns) деплоить».
- *Что значит OutOfSync?* → кластер расходится с Git.
- *Что делают self-heal и prune?* → откатывают ручные правки / удаляют лишнее, чего нет в Git.
- *Как ArgoCD откатывает релиз?* → sync на предыдущую ревизию Git.
- *Зачем sync waves/hooks?* → порядок применения (миграции до приложения и т.п.).

**Статус:** 🔴

### GO-03. App-of-apps и ApplicationSet (масштаб)
**За 30–60 сек:** **App-of-apps** — одно Application управляет набором других Application (бутстрап целого кластера одной точкой входа). **ApplicationSet** — генерирует Applications по шаблону из генератора (список, кластеры, папки Git) — для мультикластера/мультиокружения без копипаста.

**Глубокий ответ:** App-of-apps: родительское Application содержит манифесты дочерних Application → разворачиваешь всё окружение одним применением. ApplicationSet идёт дальше — генераторы (list, cluster, git directory/file, matrix) автоматически плодят Applications: например, «выкатить этот набор сервисов во все N кластеров» или «по приложению на каждую папку в Git». Это решает масштаб: десятки окружений/кластеров без ручного создания каждого Application.

**Follow-ups:**
- *Зачем app-of-apps?* → бутстрап и управление множеством приложений из одной точки.
- *Что такое ApplicationSet и его генераторы?* → шаблонная генерация Applications (list/cluster/git/matrix).
- *Как выкатить в N кластеров?* → ApplicationSet с cluster-генератором.

**Статус:** 🔴

### GO-04. Jenkins — pipeline, agents, shared libraries, граница CI/CD
**За 30–60 сек:** Jenkins — CI-сервер. Pipeline as code в Jenkinsfile: **declarative** (структурированный `pipeline{}`) против **scripted** (полный Groovy, гибче). Работа разбита на stages/steps. **Agents** — где исполняется (controller/agent, в k8s — эфемерные поды). **Shared libraries** — переиспользуемый код пайплайнов. Секреты — через credentials/Vault, не в коде.

**Глубокий ответ:** Declarative проще читать и поддерживать (рекомендуется), scripted — для сложной логики. Agents выносят сборку с контроллера (масштаб, изоляция); в k8s каждый билд — свежий под (чисто, эфемерно). Shared library убирает копипаст между пайплайнами. Важная для собеса мысль про **границу CI/CD в GitOps**: Jenkins делает CI (собрать, протестировать образ, **обновить тег в Git-репо манифестов**), а сам деплой делает ArgoCD (pull из Git). То есть Jenkins не лезет `kubectl apply` в прод — он коммитит в Git, дальше работает GitOps.

**Follow-ups:**
- *Declarative vs scripted pipeline?* → структурированный и читаемый vs полный Groovy и гибкий.
- *Что такое agent и зачем?* → исполнитель сборки вне контроллера; в k8s — эфемерные поды.
- *Зачем shared libraries?* → переиспользование общего кода пайплайнов.
- *Где граница CI и CD в GitOps?* → CI собирает и коммитит манифест/тег в Git; CD (ArgoCD) деплоит из Git.
- *Как не хранить секреты в Jenkinsfile?* → credentials store / Vault.

**Статус:** 🔴

### GO-05. Ansible — идемпотентность, модель, roles, jinja, vault
**За 30–60 сек:** Ansible — agentless IaC поверх SSH (push-модель). Ключевое — **идемпотентность**: повторный прогон не меняет уже корректное состояние (декларативные модули описывают желаемое состояние, а не команды). Структура: playbook → roles → tasks; inventory (хосты/группы); jinja2-шаблоны; Ansible Vault для секретов; handlers по notify.

**Глубокий ответ:** Идемпотентность достигается тем, что модули (`apt`, `copy`, `service`…) сначала проверяют состояние и меняют только при необходимости — отсюда `changed`/`ok`. Поэтому **`shell`/`command` ломают идемпотентность** (выполняются всегда) — их оборачивают в `creates`/`when` или избегают. Agentless (только SSH + Python на хосте) — плюс (нечего ставить), минус (медленнее на больших парках, push-модель не самовосстанавливается, в отличие от GitOps pull). Roles структурируют переиспользуемую автоматизацию; jinja2 шаблонизирует конфиги по переменным; Vault шифрует секреты в репозитории.

**Follow-ups:**
- *Что такое идемпотентность и почему shell её ломает?* → повторный прогон ничего не меняет; shell выполняется всегда без проверки состояния.
- *Agentless — плюсы и минусы?* → ничего не ставить на хосты vs медленнее на масштабе, нет self-heal.
- *Как хранить секреты?* → Ansible Vault (шифрование), или интеграция с HashiCorp Vault.
- *Push vs pull?* → Ansible пушит по SSH; GitOps — pull и непрерывная сверка.

**Статус:** 🟡

### GO-06. Стратегии деплоя: recreate / rolling / blue-green / canary / shadow
**За 30–60 сек:** **recreate** — погасить старое, поднять новое (есть даунтайм). **rolling** — постепенная замена подов (k8s default, K8S-12). **blue-green** — две полные среды, мгновенное переключение трафика и лёгкий откат (но ×2 ресурсов). **canary** — малый % на новую версию, наблюдаем метрики, расширяем. **shadow/mirror** — копия трафика на новую версию без ответа пользователю (тест на проде безопасно).

**Глубокий ответ:** Выбор — компромисс между риском, скоростью, ресурсами и сложностью отката. blue-green: переключение `service`/балансировщика на «зелёную» среду — откат мгновенный (вернуть на «синюю»), но держишь двойной набор. canary: точечный контроль доли (особенно через Istio, IS-07) и решение по SLI; идеален для прогрессивной доставки. shadow проверяет новую версию реальным трафиком без риска. **Отдельная боль — миграции БД** при rolling/blue-green: старая и новая версии работают одновременно, поэтому схема должна быть backward-compatible — паттерн **expand-contract** (сначала добавить совместимо, потом убрать старое).

**Follow-ups:**
- *blue-green vs canary?* → мгновенный свитч + двойные ресурсы vs постепенно по метрикам.
- *Как откатить в каждой стратегии?* → blue-green: вернуть трафик на старую среду; canary: снизить вес до 0; rolling: rollout undo.
- *Через что делают canary?* → Istio/ingress веса, Argo Rollouts/Flagger.
- *Проблема БД-миграций при rolling/blue-green?* → две версии сразу → схема backward-compatible (expand-contract).
- *Зачем shadow?* → проверить новую версию боевым трафиком без влияния на пользователей.

**Статус:** 🔴

### GO-07. Helm vs Kustomize — упаковка и шаблонизация манифестов

**Суть:** Helm — пакетный менеджер k8s с шаблонизацией (Go templates) и версионируемыми релизами; Kustomize — без шаблонов, патчит валидный YAML оверлеями под окружение.

**За 30–60 сек:** **Helm chart** = `Chart.yaml` (метаданные) + `values.yaml` (параметры) + `templates/` (манифесты как Go-шаблоны). `helm install/upgrade` подставляет values в шаблоны и применяет результат как единый **Release** с историей ревизий — `helm rollback` откатывает мгновенно. **Kustomize** шаблонов не использует: есть `base` (обычные валидные YAML) и `overlays` (патчи под dev/stage/prod), `kustomize build` накладывает патчи на base и генерит финальные манифесты; встроен в kubectl (`kubectl apply -k`).

**Глубокий ответ:** Helm удобен для распространения переиспользуемых пакетов (публичные чарты Bitnami, Prometheus, сам Istio ставится Helm-чартом) — один чарт параметризуется values под разные окружения/клиентов. Цена — шаблонизация текстом: `templates/*.yaml` до рендера не валидный YAML, а Go-шаблон, поэтому синтаксическую ошибку ловишь только на `helm template`/`--dry-run`, а сложные `{{- if }}`/`range` тяжело читать. Важный исторический момент безопасности: в **Helm 2** был **Tiller** — server-side компонент внутри кластера с широкими правами, частая мишень для эскалации; в **Helm 3** его убрали — всё стало клиент-side, права = права того, кто выполняет `helm` (обычный k8s RBAC, K8S-15). Kustomize идёт от другой идеи: не шаблонизировать, а декларативно патчить готовый YAML (`strategicMerge` или `patchesJson6902`) — diff между `overlays/dev` и `overlays/prod` читается как список конкретных отличий, это нагляднее для *своих* манифестов под несколько окружений, но хуже подходит для распространения пакета наружу (нет единого набора параметров-«ручек», как values.yaml). В GitOps (ArgoCD, GO-02) оба — нативные источники Application, и их можно комбинировать: взять сторонний Helm-чарт и поверх наложить свой Kustomize-оверлей.

**Follow-ups:**
- *Чем Helm отличается от Kustomize по подходу?* → шаблонизация с параметрами (values) vs декларативный патчинг уже валидного YAML.
- *Что такое Helm release и зачем rollback?* → зафиксированная установленная версия чарта с историей ревизий; откат — одна команда на предыдущую.
- *Что убрали в Helm 3 и почему это важно для безопасности?* → Tiller (server-side, широкие права в кластере); теперь клиент-side, права = RBAC вызывающего.
- *Когда Kustomize, а когда Helm?* → свои манифесты под dev/stage/prod — чаще Kustomize (наглядные патчи); переиспользуемые/сторонние пакеты — Helm (параметризация).
- *Можно ли использовать оба вместе?* → да, ArgoCD Application поддерживает Helm-чарт с Kustomize-оверлеем поверх.

**Статус:** 🔴

### GO-08. Terraform — IaC для инфраструктуры: state, providers, план/apply

**Суть:** Terraform декларативно описывает инфраструктуру (облако, DNS, сети) через providers, хранит соответствие «код ↔ реальные ресурсы» в state и перед любым изменением показывает план — что именно создаст/поменяет/удалит.

**За 30–60 сек:** Terraform — Infrastructure as Code инструмент HashiCorp: пишешь `.tf`-файлы (HCL) с желаемой инфраструктурой (VM, VPC, DNS-записи, managed БД…), провайдер (AWS/GCP/k8s/…) переводит это в API-вызовы конкретной платформы. `terraform plan` показывает дифф между кодом и текущим состоянием без применения; `terraform apply` применяет. **State** — файл (`terraform.tfstate`), в котором Terraform хранит соответствие «ресурс в коде ↔ реальный ID в облаке»; без него Terraform не знает, что уже создано.

**Глубокий ответ:** State — самая частая тема глубоких вопросов про Terraform. Он должен жить в **remote backend** (S3+DynamoDB-lock, Terraform Cloud, GCS) с блокировкой (state lock) — иначе два инженера, применяющих `apply` одновременно, повредят state гонкой. Потеря/рассинхрон state — тяжёлый инцидент: Terraform либо решит, что ресурсов не существует, и попытается создать дубликаты, либо (если ресурс переименован/удалён руками мимо Terraform) не увидит расхождения до следующего `plan` — отсюда правило «не трогать managed-Terraform ресурсы руками» (тот же принцип drift, что в GitOps, GO-01, только для инфраструктуры, а не k8s-манифестов). **Модули** (`module`) — переиспользуемые куски конфигурации (аналог Helm-чарта, GO-07, но для инфраструктуры, а не k8s-объектов). `terraform import` — забрать под управление уже существующий ресурс, созданный руками. Ключевое отличие от Ansible (GO-05): Terraform декларативен и заточен под **создание/жизненный цикл** ресурсов (провижининг, граф зависимостей ресурсов), Ansible — про **конфигурацию** уже существующих машин (что там установлено/запущено); частая связка — Terraform поднимает VM/кластер, Ansible донастраивает ОС/софт внутри.

**Follow-ups:**
- *Что такое state и почему он критичен?* → соответствие код↔реальные ресурсы; без него Terraform не знает, что уже создано.
- *Почему state держат в remote backend с локом?* → чтобы параллельный apply не повредил state гонкой (S3+DynamoDB lock, Terraform Cloud).
- *Что будет, если ресурс поменяли руками мимо Terraform?* → drift; Terraform не узнает об этом до следующего plan, дальше может откатить изменение или разъехаться со стейтом.
- *Terraform vs Ansible — в чём разница ролей?* → Terraform — провижининг/жизненный цикл ресурсов инфраструктуры; Ansible — конфигурация уже существующих машин.
- *Зачем terraform plan перед apply?* → показать точный дифф (создаст/поменяет/удалит) до применения, без сюрпризов.

**Статус:** 🔴

### GO-09. HashiCorp Vault — секреты, seal/unseal, dynamic secrets

**Суть:** Vault хранит секреты централизованно и умеет выдавать динамические, короткоживущие креды (например, к БД) вместо статических паролей — секрет существует минимально нужное время и автоматически отзывается.

**За 30–60 сек:** Vault — сервер управления секретами: хранит статические секреты (KV-движок), но главная ценность — **dynamic secrets**: по запросу генерит временные креды (например, логин/пароль в Postgres с TTL) через соответствующий secrets engine, а по истечении TTL сам их отзывает. Аутентификация клиентов — через auth methods (Kubernetes ServiceAccount token, AppRole, LDAP…), после чего клиент получает Vault token с политикой (policy), ограничивающей, какие пути секретов ему доступны. В k8s секреты попадают в под через Vault Agent Injector (sidecar) или CSI-провайдер — а не через нативный k8s Secret (K8S-08), который не шифруется по умолчанию.

**Глубокий ответ:** **Seal/unseal** — фундаментальная механика Vault: данные на диске зашифрованы мастер-ключом, и после каждого рестарта Vault стартует в состоянии **sealed** (не может расшифровать ничего, даже собственную конфигурацию секретов), пока не получит достаточное число частей мастер-ключа (**Shamir's Secret Sharing** — ключ разбит на N частей, нужен порог из K, чтобы восстановить) — защита «даже полный дамп диска бесполезен без ключей у нескольких разных людей/систем»; на практике сегодня чаще используют auto-unseal через внешний KMS (AWS KMS/GCP KMS), чтобы не собирать операторов руками на каждый рестарт. Dynamic secrets — ключевое отличие от «Vault как просто сейф»: вместо статического пароля к БД, который утекает и живёт вечно, приложение при старте просит у Vault временные креды с TTL — при компрометации украденный секрет сам протухнет, а не будет действовать бессрочно, что резко снижает blast radius утечки. Policies (написаны на HCL) реализуют least privilege — какой auth-identity какие пути секретов может читать/писать. В k8s связка обычно такая: под аутентифицируется своим ServiceAccount JWT (auth method `kubernetes`) → Vault проверяет его через k8s API → выдаёт токен с политикой → Agent Injector кладёт секрет файлом в под до старта основного контейнера.

**Follow-ups:**
- *Что значит «Vault sealed» и как его «распечатать»?* → зашифрован мастер-ключом, нужен кворум частей ключа (Shamir) или auto-unseal через внешний KMS.
- *Что такое dynamic secrets и чем они лучше статичных?* → генерируются по запросу с TTL и автоотзывом; утечка не даёт бессрочный доступ.
- *Как под в k8s получает секрет из Vault?* → аутентификация через ServiceAccount JWT (auth method kubernetes) → policy → Agent Injector/CSI кладёт секрет в под.
- *Чем Vault Secret лучше нативного k8s Secret?* → k8s Secret — просто base64 в etcd (K8S-08); Vault — реальное шифрование, TTL, аудит, динамические креды.
- *Зачем нужен порог (threshold) в Shamir's Secret Sharing?* → чтобы ни один единственный человек/система не могли в одиночку расшифровать все секреты — нужен кворум.

**Статус:** 🔴
