# Банк вопросов — Блок 8. Отказоустойчивость / кластеризация / HA (сквозной синтез)

> Часть банка подготовки к собесу DevOps/SRE. Общий план и легенда — в `00_index.md`. Сквозная тема: собирает воедино Patroni (PG-13), Kafka (KF-02), etcd/k8s, Istio — на практике эти механизмы проверяются «насквозь», через весь стек сразу.

---

### HA-01. Базовые понятия: доступность, RTO/RPO, SPOF
**За 30–60 сек:** Доступность измеряют «девятками» (99.9% ≈ 8.76 ч простоя в год). **RTO** (Recovery Time Objective) — за сколько восстановимся. **RPO** (Recovery Point Objective) — сколько данных допустимо потерять (окно). **SPOF** (single point of failure) — единая точка отказа, которую устраняют резервированием + автоматическим failover.

**Глубокий ответ:** RTO — про время, RPO — про данные; их задаёт бизнес. Async-репликация (PG-12, KF) → RPO > 0: при аварии теряются незареплицированные транзакции (равно replication lag). Sync-репликация → RPO=0, но дороже по латентности/доступности. HA = убрать SPOF (несколько реплик, несколько зон) + быстро и автоматически переключаться. Связь с LX-14: `kernel.panic=10` — чтобы упавшая нода быстро вернулась, а не висела.

**Follow-ups:**
- *RTO vs RPO?* → время восстановления vs объём допустимой потери данных.
- *Как async-репликация влияет на RPO?* → RPO>0, окно потери = replication lag.
- *Сколько простоя в год при 99.9%?* → ~8.76 часа.
- *Что такое SPOF и как убрать?* → единая точка отказа; резервирование + автофейловер.

**Статус:** 🔴

### HA-02. Кворум и split-brain ⭐(ядро темы)
**За 30–60 сек:** **Split-brain** — после сетевого раздела две части кластера считают себя главными → расходятся и портят данные. **Кворум** (большинство, N/2+1) это предотвращает: действовать может только большинство, меньшинство само себя выключает (fencing). Поэтому берут **нечётное** число узлов (3, 5) — чтобы большинство всегда определялось.

**Глубокий ответ:** Идея: при разрыве сети нельзя, чтобы обе половины принимали решения — иначе два «primary» разъедутся. Кворум: писать/выбирать лидера может только сторона с большинством голосов; сторона без большинства уходит в read-only/стоп. Нечётное число нод — потому что при чётном (например 2) после раздела ни у кого нет большинства, либо возможна симметрия. **Fencing / STONITH** — принудительно изолировать/выключить отделившийся узел, чтобы он не наделал дел. При потере кворума выбирают **безопасность** (стоп/read-only), а не доступность.

**Follow-ups:**
- *Что такое split-brain и чем опасен?* → два «лидера» после раздела → расхождение и порча данных.
- *Как кворум его предотвращает?* → действует только большинство, меньшинство выключается.
- *Почему нечётное число нод?* → чтобы большинство всегда однозначно определялось.
- *Что такое fencing/STONITH?* → принудительная изоляция отделившегося узла.
- *Что делать при потере кворума?* → read-only/стоп: целостность важнее доступности.

**Статус:** 🔴

### HA-03. etcd / DCS и консенсус (k8s, Patroni)
**За 30–60 сек:** etcd (хранилище состояния k8s) и DCS у Patroni работают на консенсусе (Raft) и требуют **кворума** (обычно 3 или 5 узлов). Потеря кворума → кластер уходит в read-only: k8s control plane перестаёт принимать изменения, но уже запущенные воркеры/поды продолжают работать.

**Глубокий ответ:** Raft выбирает лидера и реплицирует журнал; запись считается зафиксированной, когда её подтвердило большинство. Поэтому нечётное число (3 переживает падение 1, 5 — двух). 2 узла бессмысленны — нет большинства при разделе. При потере кворума etcd — k8s API становится read-only (нельзя создавать/менять объекты), но dataplane живёт. Это та же логика кворума (HA-02), применённая к хранилищу метаданных. У Patroni DCS играет ту же роль для Postgres-кластера (PG-13).

**Follow-ups:**
- *Сколько узлов etcd и почему нечётное?* → 3 или 5; для однозначного большинства и переживания отказов.
- *Что будет при потере кворума etcd?* → API read-only, существующие поды работают.
- *Почему не 2 узла?* → нет большинства при разделе, нельзя выбрать лидера.
- *Что такое Raft в двух словах?* → консенсус: лидер + репликация журнала с подтверждением большинством.

**Статус:** 🔴

### HA-04. HA PostgreSQL (Patroni) — поведение при отказе (см. PG-13)
**За 30–60 сек:** Patroni держит primary + реплики, лидерство — lease в DCS. Primary упал → lease истёк → живые реплики выбирают нового (с минимальным WAL-отставанием). Старый primary, вернувшись, видит в DCS, что он не лидер, и сам демотится (+ watchdog) — это спасает от split-brain. sync vs async задаёт RPO.

**Глубокий ответ:** Полный разбор — в PG-13. Здесь акцент на HA-логике: автофейловер строится на DCS-кворуме (HA-02/03), demote старого primary и fencing через watchdog. Если синхронная реплика настроена и недоступна — primary может приостановить запись (durability > availability). RPO=0 только при синхронной репликации; при async теряем lag. switchover (плановый) vs failover (аварийный).

**Follow-ups:**
- *Как Patroni избегает split-brain?* → кворум DCS + demote старого primary + watchdog/fencing.
- *RPO при async-реплике?* → больше нуля, теряем незареплицированный lag.
- *switchover vs failover?* → плановое vs аварийное переключение лидера.

**Статус:** 🔴

### HA-05. HA Kafka — RF, ISR, min.insync (см. KF-02)
**За 30–60 сек:** Replication factor 3 + `acks=all` + `min.insync.replicas=2` → переживаем падение одного брокера без потери данных. Unclean leader election выключают (не делать лидером отставшую реплику → не терять данные ценой доступности). Rack awareness разносит реплики по зонам.

**Глубокий ответ:** Разбор durability — в KF-02. HA-акцент: данные не теряются, пока жив кворум синхронных реплик (min.insync.replicas), а лидер при отказе переизбирается из ISR. unclean leader election — это явный выбор CAP: off = consistency/durability (партиция недоступна, пока нет ISR-реплики), on = availability ценой потери. Rack/zone awareness гарантирует, что реплики не на одной стойке/в одной зоне (переживаем отказ зоны).

**Follow-ups:**
- *Как Kafka не теряет данные при падении брокера?* → RF≥3, acks=all, min.insync≥2; новый лидер из ISR.
- *Tradeoff unclean leader election?* → доступность vs возможная потеря данных.
- *Зачем rack awareness?* → реплики в разных зонах → переживаем отказ зоны.

**Статус:** 🟡

### HA-06. HA на уровне Kubernetes
**За 30–60 сек:** Несколько реплик подов + **anti-affinity/topology spread** (разнести по нодам/зонам, K8S-10), **PodDisruptionBudget** (минимум живых при drain/обновлении), multi-AZ, HA control plane (≥3 мастера + кворум etcd), readiness probe (не слать трафик в неготовый под). Перед сервисом — балансировщик.

**Глубокий ответ:** Чтобы реплики не оказались на одной ноде (иначе её отказ убивает все) — pod anti-affinity (required) или topologySpreadConstraints по зонам. **PDB** защищает при добровольных нарушениях (drain ноды на апгрейд): k8s не выселит больше, чем разрешает бюджет, — апгрейд идёт без полной потери сервиса. HA control plane: несколько API-серверов за LB + etcd-кворум (HA-03). readiness (K8S-04) гарантирует, что трафик идёт только в готовые поды. Всё это вместе = нет SPOF на уровне оркестрации.

**Follow-ups:**
- *Как гарантировать, что реплики не на одной ноде/зоне?* → pod anti-affinity или topologySpreadConstraints.
- *Зачем PodDisruptionBudget?* → не дать выселить слишком много подов при drain/обновлении.
- *Как обновить ноду без даунтайма?* → cordon+drain с учётом PDB + rolling + readiness.
- *Что нужно для HA control plane?* → ≥3 API-сервера за LB и кворум etcd.

**Статус:** 🔴

### HA-07. Балансировка нагрузки и health checks
**За 30–60 сек:** Балансировщик распределяет трафик и **выводит нездоровые бэкенды** из ротации по health check. Active health check — LB сам опрашивает бэкенды; passive — судит по реальным ответам (ошибки/таймауты). L4 (по TCP) vs L7 (по HTTP, умнее). Алгоритмы: round-robin, least-connections и др.

**Глубокий ответ:** Health check — основа отказоустойчивости трафика: упал бэкенд → LB перестаёт слать на него. Active (явные пробы) быстрее замечает, passive (по факту ошибок) ловит реальные проблемы. L7-LB видит HTTP (маршрутизация по пути/заголовку, ret) — это k8s Ingress, Nginx upstream, Istio. Связь с readiness (K8S-04, под выходит из endpoints), Istio outlier detection (IS-06, circuit breaking) и Nginx upstream health.

**Follow-ups:**
- *Active vs passive health check?* → LB сам опрашивает vs судит по реальным ответам.
- *Что делает LB при падении бэкенда?* → выводит его из ротации по health check.
- *L4 vs L7 балансировка?* → по TCP vs по HTTP (умнее: пути, заголовки, ретраи).
- *Как это связано с readiness probe?* → неготовый под убирается из endpoints Service.

**Статус:** 🔴

### HA-08. HA ClickHouse: репликация, Keeper/ZooKeeper, шардирование

**Суть:** ClickHouse отделяет репликацию (копии одних данных, отказоустойчивость) от шардирования (разные данные на разных узлах, масштаб); координацию реплик держит ZooKeeper/ClickHouse Keeper по тому же принципу кворума, что и Patroni/etcd.

**За 30–60 сек:** **ReplicatedMergeTree** — движок-обёртка над MergeTree (CH-01), которая реплицирует вставленные куски (parts) на другие реплики через журнал в координаторе (исторически ZooKeeper, сейчас чаще встроенный **ClickHouse Keeper** — Raft-совместимая замена без внешней Java-зависимости). **Шардирование** — отдельная ось: данные делятся между независимыми группами реплик (шардами) по ключу, запрос к `Distributed`-таблице веером уходит на все шарды и агрегируется. Реплика — про надёжность одних и тех же данных, шард — про горизонтальный объём.

**Глубокий ответ:** Репликация в CH асинхронна на уровне кусков: инсерт попадает на одну реплику, она регистрирует новый part в Keeper/ZooKeeper, остальные реплики видят запись в логе и подтягивают (fetch) сам part по сети — реплицируются уже готовые (immutable) куски, а не построчный WAL, как в Postgres. Это прямое следствие CH-01 (immutable parts + merge). Keeper/ZooKeeper здесь играет ту же роль DCS/кворума, что etcd для k8s (HA-03) и DCS для Patroni (HA-04): при потере кворума координатора кластер не может согласовывать новые реплицированные операции. `Distributed`-таблица — движок-«прокси»: сама данные не хранит, а по конфигурации кластера (шарды × реплики) рассылает запрос всем шардам параллельно и суммирует частичные результаты — отсюда типовая связка ReplicatedMergeTree (надёжность внутри шарда) + Distributed сверху (масштаб по шардам). Недоступность части реплик шарда не блокирует запись/чтение, пока жив кворум Keeper и хотя бы одна реплика шарда.

**Follow-ups:**
- *Репликация vs шардирование в CH — в чём разница осей?* → репликация — копии тех же данных (надёжность), шардирование — разные данные на разных узлах (масштаб).
- *Что реплицируется — построчно или кусками?* → готовые immutable parts, а не построчный журнал.
- *Зачем ClickHouse Keeper, если есть ZooKeeper?* → тот же протокол координации (Raft-совместимый), но без внешней JVM-зависимости, проще эксплуатировать.
- *Что делает Distributed-таблица?* → не хранит данные, рассылает запрос по шардам и агрегирует ответы.
- *Что будет при потере кворума Keeper?* → новые реплицированные операции не могут согласовываться (аналог etcd/DCS, HA-03/HA-04).

**Статус:** 🔴

### HA-09. Backup & Disaster Recovery: инструменты под RTO/RPO

**Суть:** RTO/RPO (HA-01) — это цель, а бэкапы — конкретный инструмент её достижения: у каждой системы стека свой набор (WAL-архив/pg_basebackup для Postgres, снапшоты etcd, Velero для k8s), и без регулярных restore-тестов бэкап — это просто файл, а не гарантия.

**За 30–60 сек:** **PostgreSQL:** физический бэкап (`pg_basebackup` + непрерывный архив WAL, часто через pgBackRest/WAL-G) даёт **point-in-time recovery** — восстановление на любой момент между бэкапами, а не только на момент снятия копии. **etcd:** `etcdctl snapshot save` — периодический снапшот всего состояния кластера (в т.ч. k8s-объектов); восстановление — это восстановление etcd из снапшота, а не «бэкап k8s» напрямую. **Kubernetes-приложения** (тома, манифесты, секреты): **Velero** снапшотит PV (через CSI-снапшоты облака) и манифесты объектов, умеет восстанавливать в другой кластер (миграция/DR).

**Глубокий ответ:** Важная развилка — физический vs логический бэкап БД: физический (pg_basebackup, файлы данных) быстрее восстанавливается и даёт PITR, но требует совместимой версии/архитектуры; логический (`pg_dump`) переносим между версиями/платформами, но восстанавливается медленнее (пересоздание индексов, отсутствие PITR). Тестирование восстановления — то, что часто забывают: бэкап, который ни разу не разворачивали на чистом окружении, статистически не бэкап, а недоказанное предположение; практика — регулярный (например, еженедельный) automated restore-drill с проверкой целостности. RPO навязывает частоту бэкапа/архивации (окно потери = интервал между точками восстановления, либо lag реплики при failover, HA-01), а RTO — насколько автоматизирован сам процесс восстановления (ручной `pg_restore` на 40 ГБ ночью — это RTO в часы; заранее протестированный скрипт/раннбук — RTO в минуты). Правило **3-2-1** (3 копии данных, 2 разных носителя/системы, 1 offsite/другой регион) — базовый чеклист для разговора про DR, не только конкретные цифры RTO/RPO.

**Follow-ups:**
- *Чем физический бэкап Postgres лучше логического для DR?* → быстрее восстанавливается, даёт PITR через непрерывный WAL-архив; логический переносимее между версиями, но медленнее и без PITR.
- *Что бэкапит etcdctl snapshot и чего НЕ бэкапит?* → всё состояние кластера (объекты k8s) в etcd; не бэкапит содержимое PV/файлов — для этого Velero.
- *Зачем нужны регулярные restore-drill'ы?* → непроверенный бэкап — не гарантия восстановления; DR-план нужно тестировать реально, а не только на бумаге.
- *Что такое правило 3-2-1?* → 3 копии данных, 2 разных носителя/системы, 1 копия offsite.
- *Как RPO связан с частотой архивации WAL?* → окно потери = время между последним заархивированным WAL-сегментом и моментом сбоя.

**Статус:** 🔴

## Практика

### Лаб 1. Смоделировать split-brain и увидеть кворум в действии
**Задача:** на 3-узловом etcd- или Patroni-кластере оборвать сеть так, чтобы получилось 2 изолированные группы (1 узел против 2, через `iptables DROP` между конкретными хостами или отключение сетевого сегмента в docker/vagrant). Понаблюдать, что делает меньшинство и что — большинство.
**Проверка:** сторона без кворума уходит в read-only/не может выбрать лидера; сторона с большинством продолжает работать; после восстановления сети не возникает двух лидеров одновременно.
**Закрепляет:** HA-02, HA-03.

### Лаб 2. Замерить реальные RTO/RPO при failover Patroni
**Задача:** на кластере из Лаба 1 (Блок 2) намеренно убить текущий primary во время непрерывной записи, засечь время до готовности нового primary (RTO) и определить (по LSN/по данным) объём потерянных транзакций (RPO) — сначала при sync-репликации, потом при async.
**Проверка:** цифры RTO/RPO зафиксированы для обоих режимов и соответствуют ожиданиям из теории (RPO≈0 при sync, RPO>0 и равен окну lag при async).
**Закрепляет:** HA-01, HA-04.

### Лаб 3. Kafka: durability на грани отказа кворума реплик
**Задача:** на кластере с RF=3, `min.insync.replicas=2` последовательно убить 1, затем ещё 1 брокер (итого 2 из 3) во время записи.
**Проверка:** после первого отказа запись продолжается без потерь; после второго — партиция становится недоступной для записи (ошибка, а не тихая потеря данных) — воспроизведён именно этот compromise durability > availability.
**Закрепляет:** HA-05.

### Лаб 4. Kubernetes HA: PDB против drain
**Задача:** развернуть Deployment с pod anti-affinity (реплики на разных нодах) и `PodDisruptionBudget` (например, `minAvailable: 2` из 3). Выполнить `kubectl drain` на ноду, где есть реплика, и посмотреть, как PDB ограничивает эвакуацию.
**Проверка:** drain не выселяет больше подов, чем разрешает бюджет; сервис остаётся доступным на протяжении всей операции.
**Закрепляет:** HA-06.

### Лаб 5. ClickHouse: пережить потерю реплики и потерю кворума Keeper
**Задача:** на кластере из Лаба 5 (Блок 2) сначала уронить одну реплику одного шарда (данные должны остаться доступны), затем уронить кворум Keeper (например, 2 из 3 узлов) во время попытки вставки.
**Проверка:** потеря одной реплики не влияет на чтение/запись через `Distributed`-таблицу; потеря кворума Keeper блокирует новые реплицированные операции — эффект объяснён через аналогию с etcd/DCS.
**Закрепляет:** HA-08.

### Лаб 6. Backup/DR drill с реальным замером RTO
**Задача:** сделать физический бэкап Postgres (`pg_basebackup` + непрерывный архив WAL), затем «уничтожить» кластер и восстановить его на конкретную точку времени (PITR). Отдельно — снять `etcdctl snapshot save` и восстановить etcd из снапшота. Если есть k8s-кластер под рукой — сделать Velero backup namespace и restore в другой (тестовый) кластер.
**Проверка:** для каждого сценария зафиксировано реальное время восстановления (RTO) и подтверждена целостность данных после восстановления (не просто «команда отработала без ошибок»).
