### KF-01. Kafka core: топики, партиции, offset, consumer groups
**За 30–60 сек:** Kafka — распределённый append-only лог. Топик делится на **партиции** — это единица параллелизма и порядка (порядок гарантирован **только внутри партиции**). Позиция сообщения — **offset**. Producer пишет в партицию (по hash ключа или round-robin). **Consumer group**: партиции делятся между консьюмерами группы, каждая партиция — ровно одному консьюмеру в группе.

**Глубокий ответ:** Параллелизм потребления ограничен числом партиций: консьюмеров в группе больше, чем партиций — лишние простаивают. Ключ сообщения → одна и та же партиция → сохранение порядка для связанных событий (напр. по user_id). Offset коммитится консьюмером (где остановился); хранится в служебном топике `__consumer_offsets`. Несколько групп читают один топик независимо (каждая со своим offset). Брокеры хранят партиции на диске, ретеншн по времени/размеру.

**Follow-ups:**
- *Почему порядок только внутри партиции?* → между партициями нет глобального порядка; нужен порядок — один ключ/партиция.
- *Сколько консьюмеров эффективно в группе?* → не больше числа партиций.
- *Как выбирается партиция для сообщения?* → hash(key) или round-robin без ключа.
- *Где хранится offset?* → в топике __consumer_offsets, коммитит консьюмер.

**Статус:** 🟡

### KF-02. Репликация, ISR, durability (acks, min.insync.replicas) ⭐(HA)
**За 30–60 сек:** Партиция реплицируется (replication factor); один **лидер**, остальные follower'ы. **ISR** (In-Sync Replicas) — реплики, успевающие за лидером. Producer `acks`: 0 (не ждёт), 1 (только лидер), all (все ISR). `min.insync.replicas` — сколько ISR должно подтвердить при acks=all. Лидер упал → новый выбирается из ISR.

**Глубокий ответ:** Классика durability: RF=3, `acks=all`, `min.insync.replicas=2` → запись подтверждается, только когда её приняли минимум 2 синхронные реплики, и кластер переживает падение одного брокера без потери данных. **Unclean leader election**: разрешать ли стать лидером отставшей (не-ISR) реплике? off → не теряем данные, но партиция недоступна, пока не вернётся ISR-реплика (durability > availability); on → наоборот. Это прямой разговор про CAP-компромисс.

**Follow-ups:**
- *Что такое ISR?* → реплики, не отставшие от лидера; из них выбирается новый лидер.
- *acks=all + min.insync=2 при RF=3 — что даёт?* → переживаем потерю 1 брокера без потери данных.
- *Что такое unclean leader election и его tradeoff?* → лидер из отставшей реплики: доступность ценой возможной потери данных.
- *acks=1 — чем рискуем?* → лидер подтвердил, но упал до репликации → потеря.

**Статус:** 🟡

### KF-03. Delivery guarantees: at-most / at-least / exactly-once
**За 30–60 сек:** at-most-once — коммит offset до обработки (при сбое теряем). at-least-once — обработка до коммита (при сбое дубли) — **дефолт**. exactly-once — идемпотентный producer + транзакции. Идемпотентный producer убирает дубли от ретраев; транзакции дают атомарную запись в несколько партиций + коммит offset.

**Глубокий ответ:** at-least-once — практический дефолт: лучше дубль, чем потеря, поэтому потребитель обязан быть **идемпотентным** (повторная обработка не ломает результат — upsert по ключу, дедуп). Exactly-once semantics (EOS): `enable.idempotence=true` (producer не плодит дубли при ретраях за счёт sequence number) + транзакции (`transactional.id`) для атомарности «прочитал → обработал → записал → закоммитил offset». Полноценный EOS чаще в Kafka Streams. Важно понимать: EOS — внутри Kafka; на внешние системы гарантия зависит от их идемпотентности.

**Follow-ups:**
- *Какая гарантия по умолчанию?* → at-least-once.
- *Почему at-least-once даёт дубли?* → обработали, но не успели закоммитить offset → переобработка.
- *Как получить exactly-once?* → идемпотентный producer + транзакции (или Kafka Streams EOS).
- *Зачем идемпотентность потребителя?* → чтобы дубли at-least-once не портили результат.

**Статус:** 🟡

### KF-04. Kafka Connect + CDC (Debezium)
**За 30–60 сек:** Kafka Connect — фреймворк интеграции без кода: **source**-коннекторы тянут данные в Kafka, **sink** — из Kafka во внешние системы. CDC (Change Data Capture) через Debezium читает журнал БД (WAL/binlog) и публикует изменения в Kafka. Твой кейс: Oracle/Postgres → Debezium → Kafka → sink в ClickHouse.

**Глубокий ответ:** CDC ловит изменения, **читая журнал транзакций БД**, а не опрашивая её запросами — почти без нагрузки на источник и без пропусков. Connect работает в distributed mode (масштаб, отказоустойчивость, хранит offset/конфиг в топиках). Конвертеры (JSON/Avro + Schema Registry) задают формат, SMT (Single Message Transforms) — лёгкие преобразования на лету. Так строят near-real-time репликацию из OLTP в OLAP (ClickHouse) — связь с CH-01.

**Follow-ups:**
- *Что такое CDC и зачем?* → захват изменений из журнала БД; near-real-time без нагрузки запросами.
- *Source vs sink коннектор?* → в Kafka vs из Kafka во внешнюю систему.
- *Почему Debezium читает WAL, а не делает polling?* → ловит все изменения, не грузит БД, не теряет промежуточные.
- *Зачем Schema Registry?* → согласованные схемы (Avro) и их эволюция между producer/consumer.

**Статус:** 🟡

### KF-05. Ребаланс, retention, log compaction
**За 30–60 сек:** Rebalance — перераспределение партиций между консьюмерами при изменении состава группы (кто-то вошёл/вышел/завис) → пауза потребления. Retention — сколько хранить данные (по времени/размеру). Log compaction — хранить **последнее** значение по ключу (для changelog/состояния), а не всё подряд.

**Глубокий ответ:** Классический (eager) rebalance — stop-the-world: вся группа на время теряет назначения. Поэтому частые ребалансы (флапающие консьюмеры, долгая обработка превышает `max.poll.interval.ms`) = просадки. Cooperative rebalance (incremental) перетасовывает только часть партиций. Retention удаляет старые сегменты. Compaction — иной режим очистки: оставляет последнее сообщение на ключ (удаление = tombstone) — основа хранения состояния (Kafka Streams, `__consumer_offsets`).

**Follow-ups:**
- *Что триггерит ребаланс?* → вход/выход/таймаут консьюмера, изменение числа партиций.
- *Почему ребаланс — это плохо?* → пауза потребления; cooperative смягчает.
- *Retention vs compaction?* → удалять старое по времени/размеру vs хранить последнее по ключу.
- *Зачем compaction?* → компактный снимок состояния по ключам, восстановление состояния.

**Статус:** 🟡

### OB-01. SLI / SLO / SLA / error budget ⭐(SRE-ядро)
**За 30–60 сек:** SLI (Indicator) — измеряемая метрика качества с точки зрения пользователя (доступность, latency, error rate). SLO (Objective) — целевое значение SLI (например, 99.9% запросов < 200 мс за 30 дней). SLA (Agreement) — внешний контракт с последствиями (деньги/штрафы). Error budget = 100% − SLO — допустимый объём «плохого».

**Глубокий ответ:** Хороший SLI измеряет то, что **чувствует пользователь** (latency успешных запросов, доля успешных), а не утилизацию CPU. SLO — внутренняя цель (строже SLA). **Error budget** — главный инструмент SRE: пока бюджет ошибок не исчёрпан, команда катит фичи смело; исчерпан — заморозка фич и фокус на надёжности. Это объективный способ балансировать скорость разработки и стабильность без споров. 100% SLO — антипаттерн: недостижимо и убивает скорость; цель — «достаточно надёжно».

**Follow-ups:**
- *SLI vs SLO vs SLA?* → метрика / внутренняя цель / внешний контракт с санкциями.
- *Что такое error budget и зачем?* → 100%−SLO; баланс «катить фичи vs чинить надёжность».
- *Как выбрать хороший SLI?* → то, что ощущает пользователь (успешность, latency), не ресурсы.
- *Почему 100% SLO — плохо?* → недостижимо, дорого, тормозит развитие.

**Статус:** 🔴

### OB-02. Prometheus — модель, типы метрик, PromQL, pull
**За 30–60 сек:** Prometheus — time-series БД + мониторинг с **pull-моделью**: сам периодически скрейпит endpoint `/metrics` у целей по HTTP. Метрики снабжены лейблами. Типы: counter (только растёт), gauge (вверх-вниз), histogram (бакеты, для перцентилей), summary. Exporters экспонируют метрики систем. Запросы — на PromQL.

**Глубокий ответ:** Pull удобнее push: Prometheus сам знает список целей (через service discovery, в т.ч. k8s), легко понять «жива ли цель» (up), нет проблемы регистрации. Counter всегда растёт, поэтому применяют `rate(http_requests_total[5m])` (прирост в секунду). Перцентили — через `histogram_quantile(0.99, ...)` по бакетам histogram. Агрегации `sum by (...)`, `without`. Pushgateway — для коротких batch-job (исключение из pull). Alertmanager — маршрутизация/дедуп алертов.

**Follow-ups:**
- *Pull vs push — почему pull?* → известны цели, простая проверка живости, нет регистрации/спуфинга.
- *Counter vs gauge?* → монотонно растущий (запросы) vs туда-сюда (память, очередь).
- *Как посчитать частоту ошибок?* → rate() по counter ошибок / rate() по всем.
- *Как получить p99?* → histogram_quantile по бакетам histogram-метрики.
- *Когда Pushgateway?* → короткоживущие batch-задачи, которые не успеть скрейпить.

**Статус:** 🔴

### OB-03. Grafana и методология дашбордов: RED / USE
**За 30–60 сек:** Grafana — визуализация поверх Prometheus/Loki/etc. Две методологии: **RED** (Rate, Errors, Duration) — для сервисов/запросов; **USE** (Utilization, Saturation, Errors) — для ресурсов (CPU/диск/память, мы это знаем из LX-07). Алертить лучше по **симптомам** (то, что бьёт по пользователю), а не по каждой причине.

**Глубокий ответ:** RED отвечает «как сервису»: сколько запросов (Rate), сколько падает (Errors), как долго (Duration/latency, обычно p50/p95/p99). USE отвечает «как ресурсу». Связка с SLO: дашборд показывает SLI и сжигание error budget. Принцип алертинга — symptom-based: алерт «растёт latency/ошибки у пользователя» полезнее десятка алертов про загрузку диска, которые шумят и будят зря.

**Follow-ups:**
- *RED vs USE — для чего каждый?* → RED для сервисов (запросы), USE для ресурсов.
- *Что вынести на дашборд сервиса?* → rate, errors, latency-перцентили, плюс сжигание бюджета.
- *Алертить по причинам или симптомам?* → по симптомам (ближе к пользователю), меньше шума.

**Статус:** 🔴

### OB-04. ELK + Fluent Bit (твой реальный опыт)
**За 30–60 сек:** ELK = Elasticsearch (хранение и поиск логов через инвертированный индекс, данные в шардах с репликами) + Logstash (обработка) + Kibana (UI). Fluent Bit — лёгкий лог-форвардер (на C, мало ресурсов) против Fluentd (Ruby, богаче плагинами). Pipeline Fluent Bit: input → parser → filter → output.

**Глубокий ответ:** Elasticsearch шардирует индекс (горизонтальное масштабирование) и реплицирует шарды (отказоустойчивость + параллельное чтение). Требует `vm.max_map_count=262144` (LX-09) — мапит много файлов сегментов. Fluent Bit собирает логи (файлы/контейнеры), парсит (в т.ч. динамический маппинг полей/имён файлов, что ты настраивал), фильтрует и маршрутизирует в ES/Kafka/др. Часто разворачивается DaemonSet'ом в k8s (по поду на ноду, K8S-03). Тренд — structured logging (JSON) для удобного поиска/агрегации.

**Follow-ups:**
- *Роль каждого компонента ELK?* → ES хранит/ищет, Logstash обрабатывает, Kibana визуализирует.
- *Fluent Bit vs Fluentd?* → FB легче и быстрее (C), FB меньше плагинов; FB как форвардер, Fluentd как агрегатор.
- *Что такое шарды и реплики в ES?* → горизонтальное разбиение индекса + копии для надёжности/чтения.
- *Почему ES требует vm.max_map_count?* → много mmap-сегментов (LX-09).
- *Зачем structured logging?* → парсится без регэкспов, удобный поиск/агрегация по полям.

**Статус:** 🟡

### OB-05. Distributed tracing: OpenTelemetry, span/trace, Jaeger

**Суть:** Трейс — дерево спанов, показывающее путь одного запроса через все сервисы; чтобы дерево собралось, каждый сервис должен прокинуть trace-контекст дальше — сам сервис-меш этого не сделает за приложение.

**За 30–60 сек:** **Trace** — сквозной путь одного запроса через несколько сервисов, состоит из **span'ов** (единица работы: один вызов/операция с началом-концом и метаданными). Span'ы связаны в дерево через trace ID и parent span ID — так строится картина «кто кого вызвал и сколько это заняло». **OpenTelemetry (OTel)** — де-факто стандарт: единый SDK/протокол для генерации traces/metrics/logs, агностичный к бэкенду (данные шлют в Jaeger, Tempo, Zipkin, vendor APM). **Jaeger** — популярный backend для хранения и визуализации трейсов (UI показывает waterfall-диаграмму спанов).

**Глубокий ответ:** Ключевая практическая ловушка (её стоит проговорить самому, не дожидаясь вопроса): сервис-меш (Istio, IS-05) даёт метрики/access-логи «бесплатно», потому что весь трафик и так идёт через Envoy, но трейсинг бесплатно не даёт — чтобы связать входящий span с исходящим, сервис обязан прочитать trace-заголовки (`traceparent`/`b3`) из входящего запроса и прокинуть их в исходящий; если приложение это не делает, в Jaeger вместо одного дерева на запрос будет россыпь несвязанных спанов. OpenTelemetry решает это унифицированным SDK + auto-instrumentation для популярных фреймворков (HTTP-клиенты, JDBC и т.п.), которая пробрасывает контекст автоматически, без ручного кода в каждом сервисе. **Sampling** — критичный практический вопрос: трейсить 100% запросов на высоконагруженном сервисе дорого (объём данных, latency инструментирования), поэтому используют **head-based sampling** (решение сразу, например 1% случайно) или **tail-based** (решение по факту — оставить только трейсы с ошибкой/долгой латентностью, требует буферизации). Context propagation важен и через асинхронные границы (очереди Kafka, KF-01): trace ID кладут в заголовки сообщения, иначе цепочка обрывается на границе синхронный/асинхронный вызов.

**Follow-ups:**
- *Что такое span и trace?* → span — единица работы с началом/концом, trace — дерево связанных спанов одного запроса.
- *Почему mesh не даёт трейсинг «бесплатно», в отличие от метрик?* → метрики видны на каждом хопе через Envoy без участия приложения, а связать спаны можно только зная trace-контекст, который прокидывает само приложение.
- *Что такое OpenTelemetry и зачем он нужен?* → единый vendor-agnostic стандарт SDK/протокола для traces/metrics/logs.
- *Head-based vs tail-based sampling?* → решение сэмплировать в начале (дёшево, может пропустить редкую ошибку) vs по факту результата (дороже, точнее — ловит именно проблемные трейсы).
- *Как трейс переживает Kafka?* → trace ID кладётся в заголовки сообщения, потребитель продолжает трейс из них.

**Статус:** 🔴

### OB-06. Алертинг: Alertmanager, symptom vs cause, on-call, postmortem

**Суть:** Alertmanager группирует/дедуплицирует/маршрутизирует алерты от Prometheus; хороший алертинг будит только на симптомы, бьющие по пользователю и по error budget, а не на любую аномалию метрики.

**За 30–60 сек:** Prometheus сам только считает правила (`ALERT ... IF ...`) и решает, сработало ли условие; отправкой, группировкой, дедупликацией и маршрутизацией занимается отдельный компонент — **Alertmanager**. Он группирует похожие алерты в одно уведомление (не 50 сообщений «под упал» по каждому поду, а одно «поды X флапают»), подавляет (**inhibit**) менее важные алерты, если сработал более общий (не слать «сервис недоступен», если уже сработало «вся зона недоступна»), и маршрутизирует по каналам (Slack/PagerDuty/email) по лейблам severity/team. Симптом-ориентированный алертинг (OB-03) означает: алертить на то, что реально почувствовал пользователь (latency, error rate, скорость сжигания error budget), а не на каждую причину (CPU на одной ноде, один под перезапустился).

**Глубокий ответ:** **Runbook** — заранее написанная инструкция «что делать при срабатывании конкретного алерта» (первые шаги диагностики, куда смотреть, кого эскалировать) — алерт без runbook в 3 часа ночи означает потерянное время на диагностику с нуля. **Burn rate alerting** — продвинутая техника поверх error budget (OB-01): алертить не на «SLO уже нарушен» (поздно), а на **скорость сжигания бюджета** (например, «текущими темпами бюджет на месяц кончится за 6 часов») — так серьёзную деградацию ловят быстро, но игнорируют кратковременные всплески. **Postmortem (blameless)** — разбор инцидента после восстановления: что произошло, почему не поймали раньше, что чинить системно (не «кто виноват», а «что в системе позволило этому случиться») — культурная практика SRE, уместная в блоке про наблюдаемость и SRE. **Toil** — повторяющаяся ручная операционная работа, которую SRE стремится автоматизировать/устранить, а не просто выполнять быстрее.

**Follow-ups:**
- *Что делает Alertmanager, если не сам Prometheus?* → группировка, дедупликация, inhibition, маршрутизация по каналам.
- *Что такое inhibition?* → подавление менее важного алерта, когда уже сработал более общий/критичный.
- *Зачем нужен runbook?* → чтобы дежурный не изобретал диагностику с нуля в 3 часа ночи.
- *Что такое burn rate alerting и зачем?* → алертить по скорости сжигания error budget, а не по факту нарушения SLO — ловит деградацию раньше.
- *Что такое blameless postmortem?* → разбор инцидента про систему, а не про виноватого; цель — системные исправления.
- *Что такое toil?* → повторяющаяся ручная операционная работа без долгосрочной ценности; цель SRE — сокращать её автоматизацией.

**Статус:** 🔴

### OB-07. AIOps: аномалия-детекция и ИИ-ассистированные операции

**Суть:** AIOps — это применение ML/LLM внутри самого DevOps-цикла (детекция аномалий вместо статичных порогов, авто-корреляция инцидентов, ИИ-агенты в on-call) — противоположная ось AI-инфраструктуре (Блок 10), где ИИ не нагрузка, которую эксплуатируют, а инструмент самой эксплуатации.

**За 30–60 сек:** Классический алертинг (OB-06) работает по статичным порогам («latency > 500ms»), что плохо переносится между сервисами с разным базовым уровнем нагрузки и не ловит постепенный дрейф. **Anomaly detection** обучается на исторических данных метрики и алертит на статистическое отклонение от ожидаемого паттерна (с учётом сезонности — будни/выходные, дневной цикл) без ручной настройки порога под каждый сервис. **Auto-correlation** — при массовом всплеске алертов (десятки сервисов упали одновременно из-за одной первопричины) ML-слой группирует их в один инцидент и предлагает вероятную первопричину по графу зависимостей и таймлайну изменений (деплоев, конфигов). ИИ-агенты в on-call — LLM, суммирующий длинный тред алертов/логов в понятное описание инцидента, черновик постмортема или следующий диагностический шаг для дежурного.

**Глубокий ответ:** Важно не путать это с Блоком 10 (AI-инфраструктура/MLOps) — там ИИ-система (LLM, модель) сама является продакшен-нагрузкой, которую нужно разворачивать, скейлить, защищать; здесь ИИ — инструмент, который использует сам DevOps/SRE для операционной работы, а объект наблюдения — обычная инфраструктура (та же, что в остальных блоках). Практическая ценность anomaly detection выше всего там, где порог физически невозможно подобрать вручную (метрики с сильной сезонностью, тысячи низкоуровневых сервисов с разным профилем) — но и риск выше: модель может «привыкнуть» к постепенно деградирующей норме (метрика медленно растёт неделями) и перестать её замечать как аномалию, поэтому такие системы комбинируют с жёсткими SLO-порогами (burn rate, OB-06) как страховочным контуром, а не заменяют их полностью. LLM-суммаризация инцидентов и черновики постмортемов — самое зрелое и низкорисковое применение сегодня (человек всё равно проверяет и дополняет), в отличие от полностью автономного авто-ремедиейшена (ИИ сам перезапускает/откатывает продакшен-сервис по своему решению) — это гораздо более рискованная территория (ложное срабатывание может само стать причиной инцидента), и на практике такие действия почти всегда держат за человеком-approver или ограничивают узким набором заранее провалидированных, обратимых действий (перезапуск заведомо безопасного пода, а не произвольный rollback).

**Follow-ups:**
- *Чем AIOps принципиально отличается от темы AI-инфраструктуры (Блок 10)?* → там ИИ — нагрузка, которую эксплуатируют; здесь ИИ — инструмент, которым сам DevOps/SRE эксплуатирует обычную инфраструктуру.
- *Зачем anomaly detection, если есть пороговые алерты?* → не нужно вручную подбирать порог под каждый сервис/сезонность, ловит постепенный дрейф.
- *В чём риск anomaly detection на основе исторических данных?* → модель может «привыкнуть» к медленно деградирующей норме и перестать её замечать — нужен страховочный жёсткий SLO-контур.
- *Какое применение ИИ в операциях самое зрелое сегодня?* → суммаризация инцидентов/черновики постмортемов с проверкой человеком, а не полностью автономный авто-ремедиейшен.
- *Почему полностью автономный авто-ремедиейшен рискован?* → ложное срабатывание само может стать причиной инцидента; обычно оставляют approval человека или узкий список заведомо безопасных действий.

**Статус:** 🔴

## Практика

### Лаб 1. Kafka: durability под разные бизнес-требования
**Сценарий A (платёжные события):** потеря сообщения недопустима.
**Сценарий B (метрики/телеметрия):** отдельное сообщение можно потерять, важнее throughput.
**Задача:** поднять кластер из 3 брокеров, создать топик с RF=3. Для сценария A настроить `acks=all` + `min.insync.replicas=2`, `unclean.leader.election=false`; для сценария B — `acks=1`, `unclean.leader.election=true`. Во время непрерывной записи убить один брокер, затем (отдельным прогоном) два из трёх.
**Проверка:** в сценарии A потеря одного брокера не теряет подтверждённых записей, потеря двух делает партицию недоступной (но не тихо теряющей данные); в сценарии B кластер продолжает принимать запись даже с деградацией, но можно показать потерю сообщений при `acks=1`.
**Закрепляет:** KF-02, HA-05.

### Лаб 2. Rebalance: eager vs cooperative
**Задача:** запустить consumer group из 3+ консьюмеров с классической (eager) стратегией ребаланса, добавить/убить консьюмера под нагрузкой и замерить паузу обработки (`max.poll.interval.ms` и лаг по времени). Переключить на `cooperative-sticky` и повторить эксперимент.
**Проверка:** видна и измерена разница в паузе потребления между стратегиями на одинаковом сценарии входа/выхода консьюмера.
**Закрепляет:** KF-05.

### Лаб 4. Наблюдаемость: Prometheus + Alertmanager от recording rule до алерта

Специально сгенерировать всплеск ошибок и посмотреть путь от метрики до уведомления.
**Проверка:** алерт приходит один раз (не спамом на каждый под), с понятным текстом, который можно превратить в runbook.

### Лаб 5. Distributed tracing через асинхронную границу
**Задача:** инструментировать 3 связанных сервиса через OpenTelemetry SDK (HTTP-вызов между первыми двумя, третий получает событие через Kafka). ### Лаб 7. AIOps: anomaly detection против статичного порога
**Задача:** взять метрику с выраженной сезонностью (например, синтетический трафик с дневным циклом + шум), настроить статичный порог-алерт и отдельно — anomaly detection (готовый инструмент или простая модель поверх исторических данных, например скользящее среднее + доверительный интервал). Внести в метрику постепенный сдвиг (медленную деградацию на 20% за неделю) и резкий всплеск.
**Проверка:** статичный порог либо не ловит медленную деградацию (не дошла до порога), либо ложно алертит на нормальный дневной пик; anomaly detection ловит оба случая относительно ожидаемого паттерна — но можешь также показать, как модель постепенно «привыкает» к медленному сдвигу, если её не сверять с жёстким SLO-порогом.
**Закрепляет:** OB-07.
