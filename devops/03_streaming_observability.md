### KF-01. Kafka core: топики, партиции, offset, consumer groups
**За 30–60 сек:** Kafka — распределённый append-only лог. Топик делится на **партиции** — это единица параллелизма и порядка (порядок гарантирован **только внутри партиции**). Позиция сообщения — **offset**. Producer пишет в партицию (по hash ключа или round-robin). **Consumer group**: партиции делятся между консьюмерами группы, каждая партиция — ровно одному консьюмеру в группе.

**Глубокий ответ:** Параллелизм потребления ограничен числом партиций: консьюмеров в группе больше, чем партиций — лишние простаивают. Ключ сообщения → одна и та же партиция → сохранение порядка для связанных событий (напр. по user_id). Offset коммитится консьюмером (где остановился); хранится в служебном топике `__consumer_offsets`. Несколько групп читают один топик независимо (каждая со своим offset). Брокеры хранят партиции на диске, ретеншн по времени/размеру.

**Follow-ups:**
- *Почему порядок только внутри партиции?* → между партициями нет глобального порядка; нужен порядок — один ключ/партиция.
- *Сколько консьюмеров эффективно в группе?* → не больше числа партиций.
- *Как выбирается партиция для сообщения?* → hash(key) или round-robin без ключа.
- *Где хранится offset?* → в топике __consumer_offsets, коммитит консьюмер.

**Статус:** 🟡

### KF-02. Репликация, ISR, durability (acks, min.insync.replicas) ⭐(HA)
**За 30–60 сек:** Партиция реплицируется (replication factor); один **лидер**, остальные follower'ы. **ISR** (In-Sync Replicas) — реплики, успевающие за лидером. Producer `acks`: 0 (не ждёт), 1 (только лидер), all (все ISR). `min.insync.replicas` — сколько ISR должно подтвердить при acks=all. Лидер упал → новый выбирается из ISR.

**Глубокий ответ:** Классика durability: RF=3, `acks=all`, `min.insync.replicas=2` → запись подтверждается, только когда её приняли минимум 2 синхронные реплики, и кластер переживает падение одного брокера без потери данных. **Unclean leader election**: разрешать ли стать лидером отставшей (не-ISR) реплике? off → не теряем данные, но партиция недоступна, пока не вернётся ISR-реплика (durability > availability); on → наоборот. Это прямой разговор про CAP-компромисс.

**Follow-ups:**
- *Что такое ISR?* → реплики, не отставшие от лидера; из них выбирается новый лидер.
- *acks=all + min.insync=2 при RF=3 — что даёт?* → переживаем потерю 1 брокера без потери данных.
- *Что такое unclean leader election и его tradeoff?* → лидер из отставшей реплики: доступность ценой возможной потери данных.
- *acks=1 — чем рискуем?* → лидер подтвердил, но упал до репликации → потеря.

**Статус:** 🟡

### KF-03. Delivery guarantees: at-most / at-least / exactly-once
**За 30–60 сек:** at-most-once — коммит offset до обработки (при сбое теряем). at-least-once — обработка до коммита (при сбое дубли) — **дефолт**. exactly-once — идемпотентный producer + транзакции. Идемпотентный producer убирает дубли от ретраев; транзакции дают атомарную запись в несколько партиций + коммит offset.

**Глубокий ответ:** at-least-once — практический дефолт: лучше дубль, чем потеря, поэтому потребитель обязан быть **идемпотентным** (повторная обработка не ломает результат — upsert по ключу, дедуп). Exactly-once semantics (EOS): `enable.idempotence=true` (producer не плодит дубли при ретраях за счёт sequence number) + транзакции (`transactional.id`) для атомарности «прочитал → обработал → записал → закоммитил offset». Полноценный EOS чаще в Kafka Streams. Важно понимать: EOS — внутри Kafka; на внешние системы гарантия зависит от их идемпотентности.

**Follow-ups:**
- *Какая гарантия по умолчанию?* → at-least-once.
- *Почему at-least-once даёт дубли?* → обработали, но не успели закоммитить offset → переобработка.
- *Как получить exactly-once?* → идемпотентный producer + транзакции (или Kafka Streams EOS).
- *Зачем идемпотентность потребителя?* → чтобы дубли at-least-once не портили результат.

**Статус:** 🟡

### KF-04. Kafka Connect + CDC (Debezium)
**За 30–60 сек:** Kafka Connect — фреймворк интеграции без кода: **source**-коннекторы тянут данные в Kafka, **sink** — из Kafka во внешние системы. CDC (Change Data Capture) через Debezium читает журнал БД (WAL/binlog) и публикует изменения в Kafka. Твой кейс: Oracle/Postgres → Debezium → Kafka → sink в ClickHouse.

**Глубокий ответ:** CDC ловит изменения, **читая журнал транзакций БД**, а не опрашивая её запросами — почти без нагрузки на источник и без пропусков. Connect работает в distributed mode (масштаб, отказоустойчивость, хранит offset/конфиг в топиках). Конвертеры (JSON/Avro + Schema Registry) задают формат, SMT (Single Message Transforms) — лёгкие преобразования на лету. Так строят near-real-time репликацию из OLTP в OLAP (ClickHouse) — связь с CH-01.

**Follow-ups:**
- *Что такое CDC и зачем?* → захват изменений из журнала БД; near-real-time без нагрузки запросами.
- *Source vs sink коннектор?* → в Kafka vs из Kafka во внешнюю систему.
- *Почему Debezium читает WAL, а не делает polling?* → ловит все изменения, не грузит БД, не теряет промежуточные.
- *Зачем Schema Registry?* → согласованные схемы (Avro) и их эволюция между producer/consumer.

**Статус:** 🟡

### KF-05. Ребаланс, retention, log compaction
**За 30–60 сек:** Rebalance — перераспределение партиций между консьюмерами при изменении состава группы (кто-то вошёл/вышел/завис) → пауза потребления. Retention — сколько хранить данные (по времени/размеру). Log compaction — хранить **последнее** значение по ключу (для changelog/состояния), а не всё подряд.

**Глубокий ответ:** Классический (eager) rebalance — stop-the-world: вся группа на время теряет назначения. Поэтому частые ребалансы (флапающие консьюмеры, долгая обработка превышает `max.poll.interval.ms`) = просадки. Cooperative rebalance (incremental) перетасовывает только часть партиций. Retention удаляет старые сегменты. Compaction — иной режим очистки: оставляет последнее сообщение на ключ (удаление = tombstone) — основа хранения состояния (Kafka Streams, `__consumer_offsets`).

**Follow-ups:**
- *Что триггерит ребаланс?* → вход/выход/таймаут консьюмера, изменение числа партиций.
- *Почему ребаланс — это плохо?* → пауза потребления; cooperative смягчает.
- *Retention vs compaction?* → удалять старое по времени/размеру vs хранить последнее по ключу.
- *Зачем compaction?* → компактный снимок состояния по ключам, восстановление состояния.

**Статус:** 🟡

### OB-01. SLI / SLO / SLA / error budget ⭐(SRE-ядро)
**За 30–60 сек:** SLI (Indicator) — измеряемая метрика качества с точки зрения пользователя (доступность, latency, error rate). SLO (Objective) — целевое значение SLI (например, 99.9% запросов < 200 мс за 30 дней). SLA (Agreement) — внешний контракт с последствиями (деньги/штрафы). Error budget = 100% − SLO — допустимый объём «плохого».

**Глубокий ответ:** Хороший SLI измеряет то, что **чувствует пользователь** (latency успешных запросов, доля успешных), а не утилизацию CPU. SLO — внутренняя цель (строже SLA). **Error budget** — главный инструмент SRE: пока бюджет ошибок не исчёрпан, команда катит фичи смело; исчерпан — заморозка фич и фокус на надёжности. Это объективный способ балансировать скорость разработки и стабильность без споров. 100% SLO — антипаттерн: недостижимо и убивает скорость; цель — «достаточно надёжно».

**Follow-ups:**
- *SLI vs SLO vs SLA?* → метрика / внутренняя цель / внешний контракт с санкциями.
- *Что такое error budget и зачем?* → 100%−SLO; баланс «катить фичи vs чинить надёжность».
- *Как выбрать хороший SLI?* → то, что ощущает пользователь (успешность, latency), не ресурсы.
- *Почему 100% SLO — плохо?* → недостижимо, дорого, тормозит развитие.

**Статус:** 🔴

### OB-02. Prometheus — модель, типы метрик, PromQL, pull
**За 30–60 сек:** Prometheus — time-series БД + мониторинг с **pull-моделью**: сам периодически скрейпит endpoint `/metrics` у целей по HTTP. Метрики снабжены лейблами. Типы: counter (только растёт), gauge (вверх-вниз), histogram (бакеты, для перцентилей), summary. Exporters экспонируют метрики систем. Запросы — на PromQL.

**Глубокий ответ:** Pull удобнее push: Prometheus сам знает список целей (через service discovery, в т.ч. k8s), легко понять «жива ли цель» (up), нет проблемы регистрации. Counter всегда растёт, поэтому применяют `rate(http_requests_total[5m])` (прирост в секунду). Перцентили — через `histogram_quantile(0.99, ...)` по бакетам histogram. Агрегации `sum by (...)`, `without`. Pushgateway — для коротких batch-job (исключение из pull). Alertmanager — маршрутизация/дедуп алертов.

**Follow-ups:**
- *Pull vs push — почему pull?* → известны цели, простая проверка живости, нет регистрации/спуфинга.
- *Counter vs gauge?* → монотонно растущий (запросы) vs туда-сюда (память, очередь).
- *Как посчитать частоту ошибок?* → rate() по counter ошибок / rate() по всем.
- *Как получить p99?* → histogram_quantile по бакетам histogram-метрики.
- *Когда Pushgateway?* → короткоживущие batch-задачи, которые не успеть скрейпить.

**Статус:** 🔴

### OB-03. Grafana и методология дашбордов: RED / USE
**За 30–60 сек:** Grafana — визуализация поверх Prometheus/Loki/etc. Две методологии: **RED** (Rate, Errors, Duration) — для сервисов/запросов; **USE** (Utilization, Saturation, Errors) — для ресурсов (CPU/диск/память, мы это знаем из LX-07). Алертить лучше по **симптомам** (то, что бьёт по пользователю), а не по каждой причине.

**Глубокий ответ:** RED отвечает «как сервису»: сколько запросов (Rate), сколько падает (Errors), как долго (Duration/latency, обычно p50/p95/p99). USE отвечает «как ресурсу». Связка с SLO: дашборд показывает SLI и сжигание error budget. Принцип алертинга — symptom-based: алерт «растёт latency/ошибки у пользователя» полезнее десятка алертов про загрузку диска, которые шумят и будят зря.

**Follow-ups:**
- *RED vs USE — для чего каждый?* → RED для сервисов (запросы), USE для ресурсов.
- *Что вынести на дашборд сервиса?* → rate, errors, latency-перцентили, плюс сжигание бюджета.
- *Алертить по причинам или симптомам?* → по симптомам (ближе к пользователю), меньше шума.

**Статус:** 🔴

### OB-04. ELK + Fluent Bit (твой реальный опыт)
**За 30–60 сек:** ELK = Elasticsearch (хранение и поиск логов через инвертированный индекс, данные в шардах с репликами) + Logstash (обработка) + Kibana (UI). Fluent Bit — лёгкий лог-форвардер (на C, мало ресурсов) против Fluentd (Ruby, богаче плагинами). Pipeline Fluent Bit: input → parser → filter → output.

**Глубокий ответ:** Elasticsearch шардирует индекс (горизонтальное масштабирование) и реплицирует шарды (отказоустойчивость + параллельное чтение). Требует `vm.max_map_count=262144` (LX-09) — мапит много файлов сегментов. Fluent Bit собирает логи (файлы/контейнеры), парсит (в т.ч. динамический маппинг полей/имён файлов, что ты настраивал), фильтрует и маршрутизирует в ES/Kafka/др. Часто разворачивается DaemonSet'ом в k8s (по поду на ноду, K8S-03). Тренд — structured logging (JSON) для удобного поиска/агрегации.

**Follow-ups:**
- *Роль каждого компонента ELK?* → ES хранит/ищет, Logstash обрабатывает, Kibana визуализирует.
- *Fluent Bit vs Fluentd?* → FB легче и быстрее (C), FB меньше плагинов; FB как форвардер, Fluentd как агрегатор.
- *Что такое шарды и реплики в ES?* → горизонтальное разбиение индекса + копии для надёжности/чтения.
- *Почему ES требует vm.max_map_count?* → много mmap-сегментов (LX-09).
- *Зачем structured logging?* → парсится без регэкспов, удобный поиск/агрегация по полям.

**Статус:** 🟡
