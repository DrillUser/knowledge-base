# Банк вопросов — Блок 6. Istio / Service Mesh ⭐

> Часть банка подготовки к собесу DevOps/SRE. Общий план и легенда — в `00_index.md`. **Любимая тема интервьюера** — сюда копают глубже всего. Опирается на Kubernetes (Блок 5) и Linux-сеть (LX-10).

---

### IS-01. Что такое service mesh и зачем он? Что такое sidecar
**За 30–60 сек:** Service mesh — инфраструктурный слой для коммуникации сервис-сервис: выносит из приложения управление трафиком, безопасность (mTLS) и наблюдаемость в инфраструктуру. Реализуется **sidecar**-прокси (Envoy) рядом с каждым подом, который перехватывает весь входящий/исходящий трафик. Приложение о mesh не знает.

**Глубокий ответ:** Без mesh каждое приложение само тащит логику ретраев, таймаутов, mTLS, метрик — на разных языках, по-разному. Mesh выносит это в единый прокси. Sidecar (Envoy) подсаживается в под и через **iptables-редирект** (LX-10) заворачивает на себя весь трафик пода — поэтому код менять не нужно. Минусы честно: лишний сетевой хоп (+latency), потребление ресурсов на сотнях подов, рост сложности. Поэтому появился **ambient mode** (sidecarless): общий per-node прокси (ztunnel) для L4 + опциональный waypoint для L7 — меньше накладных расходов.

**Follow-ups:**
- *Зачем mesh, если можно в коде?* → единообразно, без изменения кода, на любом языке: mTLS/retry/телеметрия из инфры.
- *Как sidecar перехватывает трафик?* → iptables-редирект внутри пода на Envoy.
- *Минусы mesh?* → +1 хоп latency, ресурсы на каждый под, сложность.
- *Что такое ambient mode?* → sidecarless: per-node ztunnel (L4) + waypoint (L7), меньше overhead.

**Статус:** 🔴

### IS-02. Архитектура: data plane (Envoy) vs control plane (istiod)
**За 30–60 сек:** **Data plane** — Envoy-прокси в каждом поде, реально проксируют трафик. **Control plane** — istiod: раздаёт прокси конфигурацию (через xDS API), управляет сертификатами (встроенный CA) и service discovery. Sidecar инжектится автоматически через mutating admission webhook (K8S-01).

**Глубокий ответ:** istiod переводит твои Istio-ресурсы (VirtualService, DestinationRule…) в низкоуровневый конфиг Envoy и пушит его всем прокси по протоколу **xDS**. Также istiod — это CA: выдаёт каждому воркладу сертификат с identity (SPIFFE) для mTLS. Инжект sidecar — mutating webhook на лейбле namespace (`istio-injection=enabled`). Важный нюанс отказоустойчивости: если **istiod упадёт**, data plane продолжает работать по последней полученной конфигурации — просто не обновляется (нет новых правил/сертификатов). Mesh не «ложится» от падения control plane.

**Follow-ups:**
- *Что делает istiod?* → конфигурирует прокси (xDS), выдаёт сертификаты (CA), service discovery.
- *Как sidecar попадает в под?* → mutating admission webhook по лейблу namespace.
- *Что будет, если istiod упадёт?* → data plane живёт по последнему конфигу, без обновлений.
- *Что такое xDS?* → API, которым control plane раздаёт конфиг Envoy-прокси.

**Статус:** 🔴

### IS-03. Traffic management: VirtualService, DestinationRule, Gateway
**За 30–60 сек:** **VirtualService** — правила маршрутизации: куда и как направить запрос (по host/path/header, с весами). **DestinationRule** — что делать с трафиком после выбора назначения: subsets (версии сервиса), балансировка, пулы соединений, outlier detection (circuit breaking). **Gateway** — точка входа/выхода трафика на границе mesh (L7), замена Ingress.

**Глубокий ответ:** Разделение ответственности: VirtualService = «как маршрутизировать» (90% на v1, 10% на v2; зеркалирование; редиректы; таймауты/ретраи), DestinationRule = «как обращаться с конечной точкой» (определяет subsets по лейблам — v1/v2, политику LB, circuit breaker). Чтобы сделать canary 90/10: в DestinationRule заводишь subset'ы v1/v2, в VirtualService задаёшь веса. Gateway описывает порты/протоколы/хосты на ingress/egress, а привязывается к нему всё тот же VirtualService.

**Follow-ups:**
- *Разница VirtualService и DestinationRule?* → маршрутизация (куда/как) vs политика обращения к назначению (subsets/LB/circuit breaking).
- *Как сделать раскатку 90/10?* → subsets в DestinationRule + веса в VirtualService.
- *Что такое subset?* → именованная группа подов сервиса по лейблам (например, версия).
- *Gateway vs k8s Ingress?* → L7-вход mesh с Envoy, гибче Ingress; правила задаёт VirtualService.

**Статус:** 🔴

### IS-04. Безопасность: mTLS, PeerAuthentication, AuthorizationPolicy ⭐
**За 30–60 сек:** **mTLS** — взаимный TLS между сайдкарами: шифрование трафика + взаимная аутентификация сервисов (identity из сертификата, выданного istiod). **PeerAuthentication** задаёт режим mTLS (STRICT/PERMISSIVE). **AuthorizationPolicy** — кто с кем может общаться (L7-RBAC: по источнику/операции).

**Глубокий ответ:** Каждый воркл получает от istiod сертификат с криптографической identity (SPIFFE ID на основе ServiceAccount). Сайдкары устанавливают mTLS автоматически — приложение не трогаем. **PERMISSIVE** (принимает и mTLS, и обычный трафик) нужен для **постепенной миграции**: включаешь mesh по частям, не ломая ещё не охваченные сервисы; затем переводишь в **STRICT** (только mTLS). AuthorizationPolicy работает на L7 (можно по HTTP-методу/пути), default-deny + явные allow — это zero-trust внутри кластера, прямо в зоне любви интервьюера к безопасности.

**Follow-ups:**
- *Что даёт mTLS?* → шифрование + взаимная аутентификация (identity сервиса), без изменения кода.
- *STRICT vs PERMISSIVE и зачем permissive?* → только mTLS vs mTLS+plaintext; permissive для плавной миграции.
- *Как сервис доказывает identity?* → сертификат от istiod CA (SPIFFE, на базе ServiceAccount).
- *На каком уровне работает AuthorizationPolicy?* → L7 (HTTP-метод/путь/источник), можно default-deny.

**Статус:** 🔴

### IS-05. Наблюдаемость в mesh (метрики, трейсы, Kiali)
**За 30–60 сек:** Sidecar автоматически отдаёт golden-метрики (rate/errors/latency по каждому соединению), access-логи и участвует в distributed tracing — без изменения кода. Kiali рисует топологию mesh. Интеграция с Prometheus/Grafana/Jaeger.

**Глубокий ответ:** Поскольку весь трафик идёт через Envoy, mesh «бесплатно» даёт RED-метрики на уровне сервис-сервис и mTLS-статус соединений. **Но для distributed tracing приложение всё же должно пробрасывать trace-заголовки** (b3/traceparent) дальше по цепочке — sidecar сам не свяжет входящий и исходящий запрос без этого. Kiali визуализирует граф зависимостей, здоровье, потоки трафика — удобно показать на собесе как «вижу всю карту общения сервисов».

**Follow-ups:**
- *Что mesh даёт по observability из коробки?* → метрики rate/errors/latency, access-логи, mTLS-статус — без кода.
- *Почему для трейсинга всё же нужно менять приложение?* → надо пробрасывать trace-заголовки между входящим и исходящим запросом.
- *Что показывает Kiali?* → топологию сервисов, здоровье, потоки трафика.

**Статус:** 🔴

### IS-06. Resilience: retries, timeouts, circuit breaking, fault injection
**За 30–60 сек:** В VirtualService задаются timeout и retries (число попыток, perTryTimeout, на какие коды). В DestinationRule — **outlier detection** (circuit breaking): прокси временно выкидывает нездоровый эндпоинт из балансировки. Fault injection (искусственные задержки/ошибки) — для тестов устойчивости.

**Глубокий ответ:** Это устойчивость без кода: ретраи и таймауты на уровне прокси. Circuit breaking (outlier detection) ловит эндпоинт, который часто отвечает 5xx, и на время исключает его — не даёт «забить» падающий сервис и спасает от каскада. Осторожно с ретраями: бездумные ретраи + нагрузка = retry storm (усиление аварии) — поэтому ограничивают попытки и бюджет. Fault injection (delay/abort) позволяет проверить, как система держит сбои (chaos-подход) — хороший пример «евангелизма» практик.

**Follow-ups:**
- *Где настраиваются retry/timeout?* → в VirtualService.
- *Что такое circuit breaking и зачем?* → outlier detection в DestinationRule выкидывает нездоровый эндпоинт, предотвращает каскад.
- *Чем опасны ретраи?* → retry storm: умножение нагрузки на падающий сервис.
- *Зачем fault injection?* → намеренно вносить задержки/ошибки и проверять устойчивость.

**Статус:** 🔴

### IS-07. Canary / прогрессивная доставка через mesh ⭐(евангелизм + релизы)
**За 30–60 сек:** VirtualService с весами шлёт заданный % трафика на новую версию (subset из DestinationRule) — canary **независимо от числа подов** (в отличие от k8s rolling, где доля привязана к репликам). С Argo Rollouts/Flagger это автоматизируется: прогрессивно повышать долю по метрикам, авто-rollback при росте ошибок.

**Глубокий ответ:** Ключевое отличие от rolling update (K8S-12): mesh управляет **долей трафика**, а не числом подов — можно дать новой версии 1% при любом масштабе и смотреть метрики. Flagger/Argo Rollouts следят за SLI (error rate, latency) во время раскатки и сами повышают вес или откатывают — это и есть прогрессивная доставка. Сюда же — A/B (по заголовкам) и зеркалирование трафика (shadow) для теста на проде без влияния на пользователя.

**Follow-ups:**
- *Чем canary через mesh лучше k8s rolling?* → контроль % трафика независимо от числа реплик, решение по метрикам.
- *Что такое прогрессивная доставка?* → авто-повышение доли новой версии по SLI с авто-rollback.
- *Как сделать A/B по пользователям?* → маршрутизация VirtualService по заголовкам.
- *Что такое shadow/mirror трафик?* → копия запросов на новую версию без ответа пользователю.

**Статус:** 🔴
